# DMC3 generated STORE-overlay NBZ writer

Status: bounded Layer-1 product authoring path. This is not Capcom offline NBZ packer equivalence and is not a lossless retail-volume repacker.

## Purpose

The first writable outer-container path deliberately avoids destructive modification of retail numbered volumes:

```text
rebuilt root resource bytes
        ↓
new contiguous DMC3-N.nbz
        ↓
classic ZIP method 0 STORE
        ↓
NbzZipSource reopen
        ↓
canonical resource parse / validation
```

The recovered DMC3 member stream has a direct method-0 branch, so a DEFLATE encoder is not required for the first authoring tier.

## Bootstrap precondition

`NbzStoreOverlayWriter::build()` consumes a valid `VolumeBootstrapPlan` and writes exactly `first_missing_index`.

The safe default requires `present_after_first_gap` to be empty. If a later in-domain numbered volume already exists after the first gap, filling that gap could make the later volume newly visible to the original contiguous bootstrap and change precedence beyond the authored archive. The writer fails closed instead of activating that chain implicitly.

The output volume index must remain inside the recovered non-negative signed `%d` domain `0..INT32_MAX`.

## Member identity

Writer inputs are already-rebuilt **root runtime resource members**. Synthetic nested GDSpaces identities such as `parent::pac/slot-XXXX/...` are not archive-name authority.

For each generated member:

- path is non-empty;
- path is C-string compatible;
- path fits the ZIP 16-bit filename-length field;
- path is an ordinary file path, not a directory record;
- bytes are positive-size in this first tier;
- exact duplicate raw paths are rejected;
- the canonical DMC3 archive normalization profile `0x0E` must produce a non-empty key;
- distinct raw names collapsing to one normalized key are rejected.

The last rule prevents a writer under our control from generating a new archive whose duplicate winner would depend on CRT/input arrangement. It is SafeProductValidation derived from recovered duplicate-key ambiguity, not an invented original tie-break.

## Deterministic archive layout

Members are ordered by canonical normalized archive key. Reordering the caller's input list therefore does not alter generated bytes or archive SHA when the member set is identical.

Each local record uses:

- standard local signature `0x04034B50`;
- version-needed 2.0 product metadata;
- flags `0`;
- method `0` STORE;
- deterministic DOS time/date values;
- correct CRC32;
- compressed size == uncompressed size == materialized byte count;
- exact local filename bytes;
- zero local extra length;
- no data descriptor.

Each central record uses:

- standard central signature `0x02014B50`;
- deterministic classic product version metadata;
- the same flags, method, CRC, sizes and filename as the local record;
- zero extra/comment lengths;
- disk start 0;
- deterministic DOS archive attribute;
- exact local-header offset.

EOCD uses:

- standard signature `0x06054B50`;
- disk values 0;
- exact generated member counts;
- exact central size and offset;
- zero archive comment.

The generated archive intentionally does not reproduce retail NTFS extra fields, timestamps or other metadata that the recovered original reader does not require.

## Classic ZIP bounds

No ZIP64 is generated. The writer rejects before emission if any classic-ZIP sentinel domain would be reached:

- generated member count must be less than `0xFFFF`;
- each member size must be less than `0xFFFFFFFF`;
- local offsets, central offset, central size and total archive size must remain below `0xFFFFFFFF`.

## Authoring receipt

The deterministic receipt records:

- output volume index and canonical `DMC3-N.nbz` filename;
- archive SHA-256 and size;
- central offset/size;
- for each member: raw logical path, normalized archive key, CRC32, size, local-header offset and data offset.

The receipt does not pretend the output has source `ByteProvenance`. It is authored bytes until persisted and reopened through a source.

## Reopen semantics

After persistence, `NbzZipSource` creates new source provenance for generated members. For method 0 this is expected to be:

- `direct_source_span`;
- `zip_stored`;
- new generated source authority/data offset;
- stored size == materialized size;
- generated CRC32.

A reopened generated resource must not be compared to the retail resource by physical `ResourceId` equality. Expected stable dimensions are the intended logical path/provider key, materialized bytes and format/container topology. Source ID, NBZ central index, physical offset and provenance authority are expected to change.

## First vertical regression

The writer regression exercises:

```text
PAC ResourcePayload
 -> WorkingCopy same-size edit
 -> RelativeSlotLayoutWriter (#140)
 -> generated STORE NBZ
 -> persist temp archive
 -> NbzZipSource reopen
 -> byte equality with rebuilt PAC
 -> new zip_stored provenance
 -> canonical PAC reparse/topology comparison
```

It also validates input-order determinism, post-gap activation rejection, normalized-key collision rejection, duplicate/raw invalid paths, empty-member rejection and the valid no-retail-volume `DMC3-0.nbz` case.

## Not included

- nested child reintegration into root PAC/PNST bytes;
- automatic filesystem discovery/persistence policy;
- destructive retail-volume rewrite;
- DEFLATE encoding;
- ZIP64;
- full raw retail metadata preservation;
- original-game execution receipt.

Full retail-volume repack remains a separate later tier because current `NbzZipEntry` does not retain all raw local/central metadata needed for lossless copy-through reconstruction.
