# GDSpaces Layer 3 — Original Runtime / Lifecycle subsystem audit

**Audit date:** 2026-08-25  
**Audit base:** `main@d5e2de0b0b7a2b9e8e9f697c56051ea6e8a26d43`  
**Status:** REVIEWED / NOT COMPLETE  
**Percentage estimate:** intentionally deferred until this audit is accepted.

## Audit question

Layer 3 answers what happens after a resource has been selected and its bytes are available:

```text
selected/materialized resource
 -> FileSlot / async completion
 -> LoadedResource state transition
 -> typed post-load / recursive normalization
 -> ready visibility
 -> higher-level claim/cache ownership
 -> cancellation/reset/release
 -> transition/reload/shutdown
```

L3 does not own archive parsing or logical resolver policy. Original functions belong to the Recovered Game Source Tree; GDSpaces may reproduce only the behavior needed for safe product/runtime validation.

## 1. Canonical / sufficiently closed static boundaries

### 1.1 FileSlot / request spine

Current executable evidence is strong enough not to restart the basic FileSlot model without contradiction:

- fixed 100-entry FileSlot pool;
- sync/async request spine and callback ABI substantially recovered;
- caller-owned whole-file destination behavior recovered;
- archive stored/direct and compressed stream paths bounded;
- lower backend/stream teardown ownership substantially mapped.

Exact scheduler timing and every failure code are separate bounded edges, not reasons to discard the recovered spine.

### 1.2 LoadedResource registry topology

Canonical target authority establishes:

```text
base 0x140C99D30
363 records x 0x48
seven groups counts [4,136,60,28,1,128,6]
bases [0,4,140,200,228,229,357,363]
```

High-confidence fields include group/state/subtype or index/TypeInfo or descriptor/payload/owned backing regions at the already documented offsets.

### 1.3 Generic state machine

The following lifecycle is strong at the static boundary:

```text
0 = free/unloaded
1 = acquisition/materialization in progress
2 = materialized bytes complete; typed post-load pending
3 = typed-ready / consumer-visible
4 = cancellation/invalidation pending cleanup

0 -> 1 -> 2 -> 3
1|2 -> 4 -> 0
ordinary release -> 0 when backing release succeeds
```

State 3 is a real original-runtime boundary. A product `StageBundle` or parsed payload is not state-3 equivalence by itself.

### 1.4 Typed post-load bounded family authority

Representative typed post-load anchors are established for MOD, EFM, SCM and SHW. PAC/PNST participate in recursive typed traversal. Optional ready callback before state 3 and state-3-gated consumer visibility are recovered at the bounded scope.

This does not prove exhaustive factory dispatch for every resource family.

### 1.5 Loader-node claims above LoadedResource

The higher-level `(kind, logicalId)` loader-node claim layer is distinct from the seven LoadedResource groups. Strong recovered behavior includes claim counting, zero-claim sweep into underlying release, and representative stage component kinds 0/1/2.

### 1.6 Scene/reset policy

Strong static boundaries include:

- cancellation barrier ordering;
- selective vs full registry reset;
- preserve-common transition behavior;
- group4 persistent static-effect singleton;
- group6 persistent common gameplay package set;
- stage-local StageMain/StageCfg/StageEffect in dynamic group5;
- StartMenu broader full-registry reset;
- representative `st001` claim/use/release path.

`st001` remains one regression receipt, not the only stage authority.

## 2. Deliberate non-equivalence / product boundaries

### 2.1 Product ownership models must not invent a universal original refcount

The old assumption `normalized path -> one cache entry + universal refcount` is rejected. Fixed groups, dynamic group5, loader-node claims and texture-specific CPtx ownership are distinct policies.

Any GDSpaces shared-handle abstraction must remain product architecture unless an original family-specific ownership mapping is proven.

### 2.2 Product readiness is not original state 3 automatically

A resource being parsed, expanded, validated or handed to Stage Ops does not prove original typed-ready state. L3 acceptance requires original or reconstructed transition evidence through the typed post-load boundary.

### 2.3 Product cancellation hardening is not original timing equivalence

Timeouts, cycle guards, explicit fail-closed behavior and deterministic teardown may be necessary product safety. Do not report them as original scheduler/cancellation timing without direct evidence.

## 3. Unresolved reverse boundaries that really belong to L3

### L3-R1 — exact state-writer ownership and write ordering

For writes to `LoadedResource +0x04 state`, recover exact writer functions/callers and adjacent field write order for:

- `0 -> 1` initialization/start;
- `1 -> 2` completion;
- state-2 typed dispatcher and exact `2 -> 3` writer;
- complete source-state domain entering state 4;
- `4 -> 0` cleanup;
- ordinary release to 0.

Issue #88 remains the detailed reverse ledger for this target.

### L3-R2 — known field writer ownership

Tie writes to `+0x08`, `+0x18`, `+0x20`, `+0x28` and any stable additional fields to exact function/range ownership. Recover nullability and destruction semantics only where executable evidence proves them.

### L3-R3 — exhaustive typed dispatcher / unknown family behavior

Recover the exact selection key/table/branching beyond the bounded MOD/EFM/SCM/SHW set. Required questions include:

- how resource type is selected;
- unknown/unsupported family behavior;
- dependency/factory construction failure;
- whether failed post-load leaves state 2, enters cancellation, or follows another branch;
- exact state-3 write ordering relative to callbacks.

### L3-R4 — shared-owner coordination by family

Recover coordination for all fixed-record families where multiple owners/consumers can overlap. Do not infer group5 claim semantics for fixed groups or CPtx semantics for generic LoadedResource.

### L3-R5 — dynamic transition timing and teardown breadth

Static policy is strong, but complete original-process behavior remains open for:

- room transition;
- stage/mission transition;
- restart/reload;
- return to menu;
- cancellation during in-flight load;
- shutdown;
- allocation/factory failure paths;
- cross-build/profile differences.

## 4. Boundaries that are not current L3 reverse blockers

Do not restart without contradictory evidence:

- 363 x 0x48 registry topology;
- seven group counts/bases;
- generic 0/1/2/3/4 state meanings;
- major group5 dynamic-pool behavior;
- zero-claim loader-node release concept;
- representative typed post-load helpers already bounded;
- PAC/PNST recursive typed traversal;
- selective/full reset distinction;
- groups4/6 persistence and stage-local group5 behavior at the recovered scope.

L1 ZIP/PAC/PNST byte mechanics and L2 candidate/provider resolution are separate layers.

## 5. Missing L3 validation / acceptance

### L3-V1 — representative initial-load trace

Observe one original protected-build load from request through state 1, state 2, typed post-load, state 3 and first consumer visibility.

### L3-V2 — room/stage transition trace

Record retained/replaced/released records and loader-node claims across a representative transition. Tie the trace to exact resource identities from L2 and byte identities from L1.

### L3-V3 — restart/reload trace

Prove whether resources are reused, reacquired, reset or recreated, with state/claim transitions.

### L3-V4 — return-to-menu and full reset

Validate the broader StartMenu/full-registry reset boundary dynamically.

### L3-V5 — cancellation during in-flight work

Capture at least one `1|2 -> 4 -> 0` path with ordering around callbacks/backing release.

### L3-V6 — shutdown trace

Separate runtime unload/reset from process/CRT destruction and record backend/resource destruction order.

### L3-V7 — family breadth

Repeat the lifecycle receipt for enough distinct resource families to prevent one `st001`/stage path from being treated as universal.

## 6. Architecture risks

1. **State laundering:** treating product `ready` as original state 3.
2. **Universal-cache laundering:** replacing family-specific ownership with one path cache/refcount.
3. **Static-to-dynamic escalation:** treating static disassembly as timing/order proof for transitions.
4. **Stage-only overfit:** promoting one stage/resource family as the whole lifecycle model.
5. **Cross-layer collapse:** letting Stage Ops own original loader/cache semantics or letting GDSpaces own recovered game functions.
6. **Failure-path invention:** filling missing error/cancel semantics with convenient product abstractions and reporting them as recovered.

## 7. Canonical L3 work order

```text
1. state-writer/caller census and exact write ordering
2. known-field writer ownership
3. typed-dispatch breadth and failure behavior
4. shared-owner coordination by resource family
5. instrumented initial-load Level-E receipt
6. room/stage transition receipt
7. restart/reload + cancellation receipts
8. return-to-menu/full reset receipt
9. shutdown receipt
10. cross-family/cross-build reconciliation
11. final L3 acceptance audit
```

Dynamic work should use L1 byte identity and L2 selected identity as inputs so one receipt spans the same resource across all three layers.
