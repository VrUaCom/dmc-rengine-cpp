## Audit question

Layer 3 answers what happens after a resource has been selected and its bytes are available:

```text
selected/materialized resource
 -> FileSlot / async lifecycle ownership
 -> LoadedResource state transition
 -> typed post-load / recursive normalization
 -> ready visibility
 -> higher-level claim/cache ownership
 -> cancellation/reset/release
 -> transition/reload/shutdown
```

L3 does not own archive parsing or logical resolver policy. Original functions belong to the Recovered Game Source Tree; GDSpaces may reproduce only the behavior needed for safe product/runtime validation.

Stage Assembly / Stage Ops is a downstream consumer/domain layer, not Layer 3 in the canonical resource-runtime layer model.

## 1. Canonical / sufficiently closed static boundaries

### 1.1 FileSlot / request spine

Current executable evidence is strong enough not to restart the basic FileSlot model without contradiction:

- fixed 100-entry FileSlot pool;
- sync/async request spine and callback ABI substantially recovered;
- caller-owned whole-file destination behavior recovered;
- archive stored/direct and compressed stream paths bounded;
- lower backend/stream teardown ownership substantially mapped.

**Boundary rule:** FileSlot byte-read mechanics can support L1; FileSlot request ownership, scheduling, completion, cancellation and close lifetime are L3.

### 1.2 LoadedResource registry topology

Canonical target authority establishes:

```text
base 0x140C99D30
363 records x 0x48
seven groups counts [4,136,60,28,1,128,6]
bases [0,4,140,200,228,229,357,363]
```

The 2026-08-26 raw pass additionally reconfirms registry initialization ordering:

```text
record state = 0
 -> initialize record+0x28 backing baseline
 -> later assign group field from the group count/base tables
```

The backing baseline helper at `0x1403376F0` initializes the observed subobject fields at `+0x08/+0x10/+0x18/+0x1C` to their empty values. Stronger semantic names remain evidence-gated.

### 1.3 Generic state machine and exact central ordering

The following lifecycle is strong at the static boundary:

```text
0 = free/unloaded
1 = acquisition/materialization in progress
2 = materialized bytes complete; typed post-load pending
3 = typed-ready / consumer-visible
4 = cancellation/invalidation pending cleanup

0 -> 1 -> 2 -> 3
1|2 -> 4 -> 0
```

The reacquired EXE closes more exact ordering:

- `0x1401B84E0`: writes descriptor/type authority at `+0x18`, establishes backing/payload state including `+0x20`, calls the materialization dispatcher `0x1401B8CA0`, and publishes state `1` only after that dispatch succeeds;
- `0x1401B8DC0`: normal completion callback publishes state `2`; an unusual low-bit-tag/sentinel branch remains unresolved and must not be semantically invented;
- `0x1401B92D0`: for state-2 records performs typed post-load, then the optional callback at `+0x10`, then publishes state `3`;
- `0x1401B8430`: scans the whole registry and changes only source states `1` or `2` to state `4`; states `0`, `3` and `4` are not relabeled by that canonical writer;
- `0x1401B84B0`: quiescence is true only when every one of the 363 records is state `0` or `3`; any `1`, `2` or `4` keeps the registry non-quiescent;
- `0x1401B8F00`: cancellation cleanup writes `4 -> 0` before invoking backing release and does not use that release result to restore state;
- `0x1401B9530`: ordinary owner release invokes backing release first and publishes state `0` only on backing-release success;
- `0x1401B9560` / `0x1401B95E0`: group/full reset invoke backing release and then force state `0` unconditionally.

Therefore there are at least three distinct state-zero policies: ordinary conditional release, cancellation cleanup, and forced group/full reset. They must not be collapsed into one generic `release()` semantic.

State 3 is a real original-runtime boundary. A product `StageBundle` or parsed payload is not state-3 equivalence by itself.

### 1.4 L1/L3 materialization seam

`0x1401B8CA0` is a mixed boundary function:

- representation/materialization branch mechanics belong to L1 evidence;
- its boolean success controls whether the caller publishes L3 state `1`.

Do not classify the entire function as L1 or L3 merely by address. The ownership is semantic at the call/result boundary.

### 1.5 Typed post-load bounded family authority

Representative typed post-load anchors are established for MOD, EFM, SCM and SHW. PAC/PNST participate in recursive typed traversal.

The raw pass narrows the old failure question for central dispatcher `0x1401B9FA0`:

- null input returns;
- recognized MOD/EFM/SCM/SHW families dispatch to their known helpers;
- PNST recursively dispatches non-empty children;
- unknown/unrecognized magic falls through as a no-op/return;
- the dispatcher does not return a success/failure value consumed by `0x1401B92D0`;
- after dispatcher return, `0x1401B92D0` still performs optional callback and then publishes state `3`.

Thus the older hypothesis that an unknown/default branch in this central dispatcher might itself leave the record in state `2` is **rejected for this path**. Factory/dependency failures outside this dispatcher remain separate open targets.

One odd EF-family comparison branch remains mechanically observed but semantically unresolved; do not name it without stronger evidence.

### 1.6 Loader-node claims above LoadedResource

The higher-level `(kind, logicalId)` loader-node claim layer is distinct from the seven LoadedResource groups. Strong recovered behavior includes claim counting, zero-claim sweep into underlying release, and representative stage component kinds 0/1/2.

Direct canonical anchors remain:

- `0x1401AE220` claim increment;
- `0x1401AF6A0` claim decrement;
- `0x1401AF6F0` zero-claim sweep/release.

### 1.7 Group-5 dynamic pool exhaustion edge

`0x1401B8DF0` scans group 5 for the first state-0 record and writes family-specific `+0x08` metadata before calling generic acquisition.

The reacquired function contains no graceful no-free-record branch before the selected-record write. The bounded interpretation is that group-5 capacity is treated as a hard runtime invariant; this routine is **not** evidence of a safe exhaustion policy. DMC Rengine/GDSpaces must not copy this unsafe edge as product behavior.

### 1.8 Scene/reset policy

Strong static boundaries include:

- cancellation barrier ordering;
- selective vs full registry reset;
- preserve-common transition behavior;
- group4 persistent static-effect singleton;
- group6 persistent common gameplay package set;
- stage-local StageMain/StageCfg/StageEffect in dynamic group5;
- StartMenu broader full-registry reset;
- representative `st001` claim/use/release path.

`st001` remains one regression receipt, not universal stage authority.

### 1.9 Runtime vs CRT vs process-lifetime shutdown

The original runtime does not expose one symmetric `ResourceRuntime::Shutdown()`.

Keep three lifetime levels separate:

1. **runtime/owner lifetime** — ordinary release, cancel `1|2 -> 4 -> 0`, group/full resets, FileSlot/backend close;
2. **CRT/static destruction** — the global LoadedResource manager and all 363 record backing subobjects are destructed through registered static/atexit destruction after application return;
3. **process-lifetime infrastructure with no recovered normal explicit teardown** — mount list, FileSlot critical section and successfully started lazy AsyncIO manager in the bounded canonical path.

Original process-lifetime behavior is evidence, not a recommendation for reconstructed product ownership.

## 2. Deliberate non-equivalence / product boundaries

### 2.1 Product ownership models must not invent a universal original refcount

The old assumption `normalized path -> one cache entry + universal refcount` is rejected. Fixed groups, dynamic group5, loader-node claims and texture-specific CPtx ownership are distinct policies.

Any GDSpaces shared-handle abstraction must remain product architecture unless an original family-specific ownership mapping is proven.

### 2.2 Product readiness is not original state 3 automatically

A resource being parsed, expanded, validated or handed to Stage Ops does not prove original typed-ready state. L3 acceptance requires original or reconstructed transition evidence through the typed post-load boundary.

### 2.3 Product cancellation hardening is not original timing equivalence

Timeouts, cycle guards, explicit fail-closed behavior and deterministic teardown may be necessary product safety. Do not report them as original scheduler/cancellation timing without direct evidence.

## 3. Unresolved reverse boundaries that really belong to L3

### L3-R1 — whole-image state-writer/caller census

The canonical central writer spine and its exact ordering are now strongly bounded. Remaining R1 work is narrower:

- classify unusual/tagged/sentinel paths such as the low-bit branch in `0x1401B8DC0` without inventing semantics;
- reconcile any family-specific direct writers outside the central spine.

### L3-R2 — known field writer ownership

Tie remaining family-specific writes/reads to `+0x08`, `+0x18`, `+0x20`, `+0x28` and additional stable fields to exact functions/callers.

The raw pass strengthens `+0x28` as a backing/owned subobject with distinct runtime-release (`0x140337710`) and destructor (`0x140337440`) behavior, but exact public semantic names for its subfields remain deliberately bounded.

### L3-R3 — typed dispatcher breadth outside the closed central default question

The central `0x1401B9FA0` unknown/default behavior is now bounded as best-effort/no-op rather than a state-2-blocking failure result.

Remaining R3 questions:

- any additional typed/factory/dependency dispatch outside this central function;
- family-specific preconditions/failures inside called helpers;
- SCM `mesh +0x28` reconciliation;
- unresolved odd EF-family branch semantics;
- whether other callers apply stricter failure policy around typed resources.

### L3-R4 — shared-owner coordination by family

Recover coordination for all fixed-record families where multiple owners/consumers can overlap. Do not infer group5 claim semantics for fixed groups or CPtx semantics for generic LoadedResource.

### L3-R5 — dynamic transition timing and teardown breadth

Static policy is strong, but complete original-process behavior remains open for:

- stage/mission transition;
- restart/reload;
- return to menu;

## 6. Architecture risks

1. **State laundering:** treating product `ready` as original state 3.
2. **Universal-cache laundering:** replacing family-specific ownership with one path cache/refcount.
3. **Static-to-dynamic escalation:** treating static disassembly as timing/order proof for transitions.
4. **Stage-only overfit:** promoting one stage/resource family as the whole lifecycle model.
5. **Cross-layer collapse:** letting Stage Ops own original loader/cache semantics or treating materialization branch mechanics as lifecycle ownership.
6. **Failure-path invention:** inventing an error branch where the central dispatcher actually performs best-effort/no-op behavior.
7. **Unsafe-original laundering:** copying the group-5 no-capacity hard invariant into safe product code.
