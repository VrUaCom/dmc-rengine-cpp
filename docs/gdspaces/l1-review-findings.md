## Що змінив `#150` — і чого він не змінив

`746b75f` (`#150`) увів `ArtifactBoundNbzZipSerializationSnapshot`: приватний конструктор, `friend class NbzZipArtifactSerializationBinder`, коментар у заголовку прямо каже «callers cannot self-declare artifact-bound authority». Біндер робить streaming SHA-256 усього артефакту, звіряє index із observation і крос-перевіряє поля.

**Партнер правий:** формулювання rev 1, ніби `valid()` — «єдиний бар'єр перед copier», більше не відповідає архітектурі. Підробити снапшот руками тепер не можна.

**Але `#150` закриває підробку, а не повноту.** Це різні властивості:

- SHA-256 біндинг доводить «ці байти взяті саме з цього файлу» — це provenance джерела;
- замощення регіонів доводить «збережені регіони покривають кожен байт того файлу» — це повнота preservation.

Repacker, що копіює «незмінені регіони», потребує **другої** властивості. Хеш каже, з якого файлу копіювати; він не каже, що регіони снапшота його покривають.

Конкретні докази на `origin/main`:

1. `NbzZipSerializationSnapshot::valid()` (`nbz_zip_serialization.cpp:446`) **побайтово ідентичний** версії на `b80aebe`. P2 і P3 не змінилися.
2. `ArtifactBoundNbzZipSerializationSnapshot::valid()` (`nbz_zip_artifact_binding.cpp:558`) **делегує** в `serialization_.valid()` і додає лише `artifact_.valid()`, збіг розміру та збіг хешу. Прогалину він **успадковує**.
3. Крос-перевірка біндера (`nbz_zip_artifact_binding.cpp:474–528`) не містить жодної логіки замощення — `grep` по `prefix|region|coverage|tile|gap` дає тільки локальні перевірки префікса.
4. **Показова асиметрія щодо P3.** Для локального запису біндер перевиводить довжину точно:
   ```cpp
   expected_local_prefix = 30 + local_name_length + local_extra_length;
   … expected_local_prefix != observed.local_prefix_bytes.size() || …   // рівність
   ```
   Для центрального — лише нерівність:
   ```cpp
   central_fixed_size + central_name_length > observed.central_record_bytes.size()  // ≤, не ==
   ```
   `extra` і `comment` центрального запису не використовуються взагалі. Тобто рівнісну перевірку явно замислювали — її просто не застосували до central record.

**Висновок:** severity P2 знижується (змагальний шлях закрито приватним конструктором; лишається ризик регресії сканера, не помітної для `valid()`), але фікс лишається вартим — він дешевий, а асиметрія в п.4 сама вказує на рішення.

## P1 — `ResourceId::canonical()` не ін'єктивна

**Місце:** `src/gdspaces/resource_id.cpp:11` · **високий** · відтворюється тестом

Склеює три керовані ззовні рядки неекранованими роздільниками:

```cpp
out << source_id << ':' << logical_path;
if (!container_chain.empty()) { out << '#' << container_chain; }
out << "@" << offset << "+" << size;
```

Жоден із `:` `#` `@` `+` не екранується і не має префікса довжини, а всі три поля можуть їх містити: `logical_path` — сира назва з ZIP central directory або з диска, а `ContainerExpander` сам будує дитячі шляхи з `::`. Поділ між `logical_path` і `container_chain` не відновлюється з ключа.

Це первинний ключ підсистеми: вузли `ResourceGraph` і обидва кінці кожного ребра, `identity_key` для дедуплікації в `ResourceKeyIndex`, ключ сесій у `project_workspace`, дедуп у `nested_relative_slot_reintegrator` і `stage_workspace_builder`, `authority_id` провенансу в `LocalDirectorySource`, серіалізоване поле в 5 райтерах маніфестів.

### Наслідок гірший, ніж описувала rev 1

Rev 1 стверджувала: другий вузол тихо втрачається, ребро не створюється. Виконання показало інше — і гірше. Оскільки `from_key == to_key`, `connect()` знаходить «обидва» кінці й **успішно** записує ребро:

```cpp
assert(graph.add(child));                                              // true
assert(!graph.add(loose));                                             // друга ідентичність відхилена
assert(graph.resource_count() == 1U);
assert(graph.connect(child.id, loose.id, ResourceRelation::contains));  // УСПІХ
assert(graph.edge_count() == 1U);
// граф тепер стверджує, що ресурс містить сам себе
```

Тобто колізія не просто втрачає ідентичність — вона фабрикує хибне `contains`-ребро вузла на самого себе. Це прямо суперечить identity rules 3, 4 і 5.

**Досяжність.** Потрібне ім'я файлу з `#` і `::` — незвично, але легально і в POSIX, і в ZIP central directory. Дефект схеми ключування, а не баг, що стріляє на типовому корпусі. Контракт спирається на цей ключ саме щоб побиті архіви **не могли** склеювати ідентичності.

**Фікс.** Префікс довжини замість роздільників. Рутина вже в кодовій базі — `append_string_field` (`container_tree_expander.cpp:33`) пише `size:value|` рівно з цієї причини.

> ⚠️ **Rev 1 помилково стверджувала, що це закриває P8/P9.** Не закриває — див. P8/P9.

## P2 — снапшот не перевіряє покриття байтів

**Місце:** `src/gdspaces/nbz_zip_serialization.cpp:446` · **середній** (знижено з високого) · відтворюється тестом

`prefix_size` ні до чого не прив'язаний, і локальні регіони не зобов'язані замощувати `[prefix_size, computed_central_start)` без дір і перекриттів. Ланцюг central directory перевіряється строго; те, заради чого документ існує, — ні.

Три різні «втратні» снапшоти проходять `valid()`: `prefix_size = 0` (12 байтів ніде не враховані), `prefix_size = computed_central_start` (ковтає весь регіон члена), урізаний `local_region_size` (осиротює хвостовий проміжок).

**Чому severity знижено:** `#150` унеможливив підробку снапшота ззовні (приватний конструктор). Лишається ризик, що регресія сканера пройде непоміченою для `valid()`, і що інваріант не є самодостатнім. Деталі — розділ «Що змінив #150».

### Виправлений фікс

Rev 1 пропонувала `prefix_size == entries.front().local_record_offset` — **це хибно**. `entries` впорядковані за central directory, фізичний порядок local records може бути іншим. Сам сканер це знає: він рахує `prefix_size` як `std::min` по всіх локальних зсувах, а регіони виводить через `upper_bound` по **відсортованих різних** зсувах.

Правильно:

1. `prefix_size == min(distinct local_record_offset)` — або `computed_central_start`, якщо записів немає;
2. відсортувати різні локальні зсуви, згрупувати аліаси (кілька central-ідентичностей на один локальний зсув);
3. пройти групи по порядку, вимагаючи, щоб кожен регіон починався там, де скінчився попередній;
4. останній регіон має завершитися точно на `computed_central_start`.

## P3 — довжина central-запису не звіряється з його ж полями

**Місце:** `src/gdspaces/nbz_zip_serialization.cpp:121` · **середній** · відтворюється тестом

`snapshot.valid()` рухає `central_cursor` на `central_record_bytes.size()` і вважає цей розмір єдиним авторитетом, але запис ніколи не перевираховує `46 + name + extra + comment` зі своїх же полів (зсуви 28/30/32).

У rev 1 це було з читання. Тепер підтверджено виконанням: якщо у збереженому 46-байтовому записі оголосити 4-байтове ім'я (зсув 28), сумлінний запис мав би бути 50 байтів — а `valid()` усе одно повертає `true`, бо обхід усе ще влучає рівно в EOCD.

**Не закривається `#150`.** Біндер робить рівнісну перевірку для локального префікса, але для центрального — лише нерівність, і не дивиться на `extra`/`comment`. Ця асиметрія і є вказівкою на фікс.

**Фікс.** У `entry.valid()` перерахувати довжину з байтів 28/30/32 і вимагати рівності з `central_record_bytes.size()`; те саме винести в крос-перевірку біндера.

## P4 — бюджет пам'яті витрачається після алокації

**Місце:** `src/gdspaces/nbz_zip_serialization.cpp:248` · **середній**

```cpp
snapshot.entries.reserve(indexed_entries.size());   // бюджет не спитано
```

`consume_metadata_budget` уперше викликається на рядку 252 і тільки для байтових обсягів. `NbzZipSerializationEntry` ≈ 104 B, тож мільйон задекларованих записів дає ~104 MB резерву навіть коли бюджет виставлено в мінімум 22.

**Уточнення партнера:** поточні docs трактують entry bookkeeping як обмежене не цим byte-budget, а `max_central_entries` джерела. Фактична поведінка від цього не змінюється, але формулювання претензії коректніше звучить так: **назва `max_metadata_bytes` вводить в оману щодо того, що саме вона стереже**, і між двома лімітами немає явного зв'язку в коді.

**Фікс.** Або списувати `entries.size() * sizeof(NbzZipSerializationEntry)` з бюджету перед `reserve`, або прибрати `reserve` і покластися на per-entry перевірки в циклі, або задокументувати розподіл відповідальності просто в заголовку.

## P5 — конструктор `WorkingCopy` без інваріанту

**Місце:** `src/gdspaces/working_copy.cpp:12` · **latent hardening** (знижено з середнього)

Конструктор бере `ResourcePayload`, лишає тільки `resource` і `bytes`, ніколи не звертається до `readable()`, викидає `diagnostics` і `byte_provenance`. Нечитабельний payload — NBZ-член, що завалив CRC, де `read()` навмисне чистить `bytes`, — стає `WorkingCopy` над порожнім буфером із валідним на вигляд SHA-256 порожнечі.

Гейт із `workspace-parser-validation-gate.md` живе в `ResourceWorkspace::enable_working_copy()`, шаром вище. Три місця будують `WorkingCopy` напряму: `runtime_synth_relative_slot_writer.cpp:293`, `nested_relative_slot_reintegrator.cpp:93` і `:327`.

**Усі три сьогодні безпечні** — кожне саме перевіряє читабельність, а layout-райтер повторно перевіряє `source.readable()`. Тому знижено до latent: це тип без власного інваріанту, а не активний баг. Спрацює тоді, коли з'явиться четвертий call site.

**Фікс.** Статична фабрика `std::optional<WorkingCopy>` з передумовою `readable()` — лягає у стиль кодової бази (пор. `ExactChildImage::from_intrinsic_resource`).

## P6 — `connect_graph` глушить усі return-значення

**Місце:** `src/gdspaces/container_expander.cpp:269` · **observability gap** (знижено з середнього)

Обидва `add()` і `connect()` — під `static_cast<void>`, жоден викликач результат не перевіряє. Провал додавання вузла означає, що ребро тихо не створюється, і граф повертається з дірою без діагностики.

**Уточнення партнера прийнято:** це насамперед прогалина спостережуваності та інваріанту, а не окремий medium corruption bug. Corruption-складова належить P1.

### Виправлений фікс

Rev 1 пропонувала «діагностика щоразу, коли `connect()` повернув `false`» — **недостатньо**. `ResourceGraph::connect()` повертає `false` щонайменше для трьох різних ситуацій, з яких одна цілком легітимна:

- `from` не знайдено;
- `to` не знайдено;
- таке ребро вже існує ← **нормально**, діагностувати не треба.

`add()` так само повертає `false` і для невалідного ресурсу, і для вже присутнього ключа.

Правильно — типізований результат замість `bool`:

```
inserted | already_exists | missing_from | missing_to | invalid_identity
```

і діагностика лише для справді помилкових варіантів.

## P8 — `find_entry` перебудовує кожен ключ на кожен пробіг

**Місце:** `src/gdspaces/nbz_zip_source.cpp:754` · **продуктивність**

```cpp
return id_for(source_id_, entry).canonical() == resource.canonical();
```

Лінійний скан, де кожен кандидат конструює повний `ResourceId` (три копії рядків), а тоді форматує ключ через `ostringstream` — з обох боків порівняння, на кожному `read()`.

> ⚠️ **Виправлення rev 1.** Rev 1 стверджувала, що P8 закривається фіксом P1. **Ні.** Перехід на `operator==` прибирає форматування рядків, але:
> - складність лишається **O(n)**;
> - `id_for()` сам конструює `ResourceId` із двома `std::string`, тож навіть `id_for(...) == resource` **не** дає zero-allocation.
>
> Це окрема задача, не побічний ефект P1.

**Фікс.** Мапа, побудована один раз у `build_index()` — або пряме порівняння полів (`entry.logical_path`, `central_index`, розмір) без конструювання `ResourceId`.

## P9 — `StageBundle::add` — O(n²)

**Місце:** `src/gdspaces/stage_bundle.cpp:15` · **продуктивність**

Кожен `add` сканує всіх наявних членів і будує канонічний рядок для кожного.

> ⚠️ **Те саме виправлення.** Перехід на `operator==` здешевлює одне порівняння, але **не** прибирає O(n²) — це лінійний скан на кожну вставку.

**Фікс.** `std::set`/hash-індекс за ідентичністю поруч із вектором членів, якщо квадратичність справді треба прибрати.

## P10 — `RuntimeSynthResult::ok()` перехешовує весь образ

**Місце:** `src/profiles/dmc3/runtime_synth_relative_slot_writer.cpp:252` · **продуктивність**

Читається як дешева перевірка статусу, а насправді викликає `receipt->valid()`, рахує SHA-256 усього вихідного образу і SHA-256 кожного дитячого спану. Один `rebuild()` хешує вихід щонайменше двічі (рядок 506 і всередині `ok()` на 524) і валідує receipt двічі (512 і всередині `ok()`). Подача результату в `from_verified_runtime_synth_result` кличе `ok()` втретє.

### Виправлений фікс

Rev 1 пропонувала на вибір: перейменувати **або** закешувати перевірений стан. **Друга опція небезпечна і знімається.**

`RuntimeSynthResult` — публічний агрегат із мутабельними `bytes` і `receipt`. Якщо один раз виставити `verified = true`, а потім хтось змінить `bytes`, кешована верифікація стає authority laundering — рівно той клас проблем, проти якого побудований увесь контракт.

Лишається:

1. Зробити вартість явною в імені — `verify_integrity()`.
2. Прибрати дубльований `receipt.valid()` на рядку 512 — це безкоштовно.
3. Кешувати **тільки** після того, як `RuntimeSynthResult` стане immutable/non-forgeable (приватні поля + фабрика, як зробили для `ArtifactBoundNbzZipSerializationSnapshot` у `#150`).

## Перевірено і відкинуто

- **Пріоритет `uppercase_ascii` над `lowercase_ascii`** — не дефект, задокументована в заголовку відновлена оригінальна поведінка (`normalize`, крок 3).
- **Неперевірений розмір після inflate** — `RawDeflate` має статус `output_size_mismatch`.
- **`read_exact` з порожнім спаном** — єдиний такий виклик далі порівнюється з непорожнім `name_bytes`.
- **Часткове перекриття спанів у nested-реінтеграції** — канонічний парсер дає спани або ідентичні (аліаси), або диз'юнктні.
- **Path traversal у `LocalDirectorySource`** — покомпонентне порівняння префікса, `weakly_canonical`, перехоплення абсолютного `logical_path`. Fail-closed коректно.

## Що перевірено і виявилося правильним

Партнер підтвердив цю частину незалежно. Кілька з цього — саме ті анти-патерни, які контракт називає поіменно:

1. **Стиснуті координати не перетворюються на дитячий lineage.** DEFLATE-батько — `transformed_source_span`, тож діти отримують `materialized_parent_span`; лише STORE-батьки передають прямі зсуви, де арифметика валідна. — `container_expander.cpp:68–110`
2. **Reuse парс-результату прив'язаний до реального вмісту** — opt-in парсера, валідний провенанс, збіг materialized-розміру, тотожність lineage і SHA-256 переданих байтів. Попадання перевикористовує лише `ContainerParseResult`. — `container_tree_expander.cpp:37–74`
3. **Ancestry-guard звільняється на всіх шляхах виходу** — сусідні аліаси не глушаться, тільки справжні цикли. — `container_tree_expander.cpp:211–309`
4. **Розріджена ідентичність слотів виживає** — усі `declared_slot_count` записів матеріалізуються, включно з порожніми. — `relative_slot_container.cpp:116–145`
5. **Protected prefix покриває заголовок і таблицю зсувів** — парсер відхиляє заповнені зсуви нижче `table_end`. — `relative_slot_writer.cpp:208–223`
6. **Runtime-synth тримає extraction span окремо від intrinsic length** — `intrinsic_size <= entry.size` проти переparsed-екстента. — `runtime_synth_…writer.cpp:243, 495`
7. **Nested-реінтеграція чесна щодо аліасів** — групування за точним `(offset, size)`, розбіжні байти відхиляються, зачеплені неавторовані аліаси розкриваються в `affected_aliases`. — `nested_relative_slot_reintegrator.cpp:264–311`
8. **Product hardening відокремлений від claims про оригінальну поведінку** — `gdspaces.nbz.safe.*` проти `gdspaces.nbz.compat.*`. — `nbz_zip_source.cpp`
9. **Зсуви ZIP-полів коректні**, членам заборонено дотягуватися в домен central directory. — `nbz_zip_source.cpp:702–713`
10. **STORE overlay-райтер робить round-trip**, receipt самостійно перевиводить кожен виданий зсув. — `nbz_overlay_writer.cpp`
11. **Цілочисельна арифметика захищена послідовно** — `checked_add`, віднімання після порівняння, недосяжний overflow-сентинел `aligned_size`.
12. **Локальні читання fail-closed поза коренем.** — `local_directory_source.cpp:27–41`

## Пріоритезація (rev 2)

**Робити першими:**

1. **P1** — б'є по всій системі ідентичності й фабрикує хибні ребра. Фікс дешевий, рутина вже в репо.
2. **P3** — асиметрія в біндері прямо вказує на рішення; закривається кількома рядками.
3. **P7** — тривіально, і треба закрити обидва місця до появи третього.

**Далі:**

4. **P2** — фікс за виправленим алгоритмом (min по різних локальних зсувах, не `entries.front()`).
5. **P6** — типізований результат замість `bool`; це рефакторинг API, не однорядковий фікс.
6. **P4** — або списувати bookkeeping з бюджету, або задокументувати розподіл лімітів.

**Продуктивність — окремою серією, не як побічний ефект P1:**

7. **P8** — індекс/мапа в `build_index()`.
8. **P9** — set/hash-індекс, якщо квадратичність реально заважає.
9. **P10** — лише перейменування + прибрати дубльований `receipt.valid()`. Кешування — тільки після immutability.
10. **P11** — індекси замість копій.

**Не чіпати зараз:** P5, P12, P13, P14 (latent/semantics), P15, P16 (спірні).

> **P8 і P9 не закриваються фіксом P1.** Це три окремі задачі, а не одна.
