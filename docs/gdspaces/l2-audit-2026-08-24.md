## Audit question

Layer 2 answers:

```text
logical request
 -> candidate construction
 -> provider-specific normalization
 -> mounted provider/source selection
 -> numbered-volume precedence
 -> normalized source lookup
 -> duplicate/ambiguity behavior
 -> exact ResourceRef identity
```

This audit distinguishes recovered original behavior, deliberate product policy, validation coverage and unresolved reverse boundaries. L1 materialization and L3 lifecycle are referenced only where they establish an L2 boundary.

## 1. Canonical / sufficiently closed boundaries

### 1.1 Generic OpenGameResource candidate branch

The bounded `OpenGameResource` branch around `0x14002FCA0` is strong enough to treat as canonical for the evidenced DMC3-HD path:

- request is reduced to basename after the last `/` or `\\`;
- six namespace candidates are constructed in this order:
  1. `GDataX360.afs/`
  2. `GData.afs/`
  3. `Video/`
  4. `afs/sound/`
  5. `SAVEDATA/`
  6. empty prefix;
- provider mask 1 performs the complete archive pass first;
- provider mask 2 performs the complete physical pass second;
- candidate construction uses the recovered `0x400` destination bound;
- basename bytes/case are preserved until provider normalization.

The `.afs/` strings remain logical namespaces. They do not establish a binary AFS backend.

### 1.2 Provider normalization primitive

`ResourcePathNormalize` behavior is strongly recovered for C-string-compatible inputs:

- `0x0E` archive profile;
- `0x0C` physical profile;
- leading/trailing separator stripping according to the bit mask;
- ASCII case transform according to the bit mask;
- `/ -> \\`;
- repeated separator collapse.

No locale/Unicode semantics are inferred.

### 1.3 Numbered NBZ bootstrap and precedence

The bootstrap family around `0x14002E930` is strong:

- executable-relative `data/dmc3` root;
- `DMC3-%d.nbz` from zero;
- first-gap stop;
- runtime-equivalent non-negative signed decimal domain `0..INT32_MAX`;
- later in-domain files after a gap are diagnostic-only;
- larger numeric suffixes are outside the recovered runtime namespace;
- physical root is registered first;
- archives register ascending but mount nodes prepend;
- effective archive precedence is highest contiguous volume to lowest.

### 1.4 Archive normalized index/search

The ZIP/NBZ lookup architecture is sufficiently strong for unique normalized keys:

- central entries remain physical identities;
- archive paths normalize with `0x0E`;
- an array of normalized-name plus central-entry pointer is sorted;
- CRT `qsort` / `bsearch` architecture is recovered;
- `.index` is not original runtime lookup authority on this path.

### 1.5 Resolver composition and ownership

Current `RuntimeResourceResolver` has the correct ownership model:

- `ISource` owns exact identity/enumeration/read only;
- `SourceRegistry` owns mounted source identity and exact-read routing;
- normalized lookup is a derived source-bound `ResourceKeyIndex`;
- no caller-owned raw `ResourceKeyIndex*` can substitute a stale index;
- archive volume precedence remains a resolver concern, not an index concern;
- a hit under an earlier namespace candidate beats a hit under a later candidate even if the later candidate exists in a higher volume;
- within one archive candidate, higher contiguous volume wins;
- all archive candidates complete before physical candidates;
- zero archive volumes correctly fall through to the physical phase.

### 1.6 Product validation already present

Current tests prove bounded product composition for:

- exact six-prefix / twelve-attempt construction;
- mixed slash/case input before provider normalization;
- embedded-NUL rejection;
- first-gap and signed-domain volume behavior;
- higher-volume precedence;
- prefix precedence as the outer ordering authority;
- archive normalization;
- no-volume physical fallback;
- stale/wrong-source index rejection;
- generated higher-volume NBZ mounted as real `NbzZipSource` and selected by `RuntimeResourceResolver` (#187);
- directory-qualified request becoming basename candidate in the generated-volume path.

These are product/CI receipts, not original-process dynamic equivalence.

## 2. Deliberate product policies that are not original-equivalent claims

### 2.1 Duplicate normalized archive keys

Recovered CRT lookup has no evidenced semantic secondary tie-break for comparator-equal normalized keys. A `bsearch` hit among equal keys is therefore not a stable semantic winner that GDSpaces may invent.

Current product policy is deliberately safer:

- preserve all distinct physical identities;
- report `ambiguous`;
- do not continue to a lower-precedence source to manufacture a winner.

This is correct product hardening, but it is not byte-for-byte original lookup equivalence for an archive that really contains comparator-equal duplicate keys.

**Acceptance consequence:** L2 needs a real-retail duplicate-key census. If the relevant retail DMC3 volumes contain no comparator-equal duplicate keys, this difference can be declared non-operative for the evidenced retail scope. If duplicates exist, dynamic/original lookup evidence is required before claiming exact winner parity for those keys.

### 2.2 Physical provider product index

The physical pass uses a source-derived `ResourceKeyIndex` with `0x0C` normalization and is explicitly tagged `product_physical_index`.

This must remain product policy. `LocalDirectorySource` uses `std::filesystem`, `weakly_canonical`, enumeration and `ifstream`; none of those prove the original type-0 backend's final Win32 path/open behavior.

### 2.3 Request safety

Embedded-NUL rejection and complete-plan failure on candidate overflow are safe product boundaries. Embedded-NUL rejection is a necessary adaptation from C-string input to `string_view`.

For the `0x400` candidate buffer, the bound itself is recovered, but current `ResourceLookupPolicy` makes the entire twelve-attempt plan invalid if any candidate overflows. Exact original continuation/abort behavior after an oversized candidate is not yet proven.

## 3. Unresolved reverse boundaries that really belong to L2

### L2-R1 — exact type-0 physical provider final path/open semantics — BLOCKING FOR FULL L2 EQUIVALENCE

After `ResourcePathNormalize(..., 0x0C)` recover the complete downstream chain:

- exact base/root join and filename construction;
- whether the normalized candidate is probed directly or transformed again;
- Win32 API/function family used for existence/open;
- flags/share/access/disposition/attributes;
- case behavior;
- exact file-vs-directory behavior;
- failure return values and how the caller distinguishes miss from backend error;
- whether any alternate-name/default branch is taken after an open failure.

This is currently the largest exact L2 gap.

### L2-R2 — oversized candidate behavior at `OpenGameResource`

The `0x400` construction destination is recovered; the exact branch after one candidate cannot fit is not. Recover whether original behavior:

- aborts the whole request;
- skips only that candidate;
- truncates/fails a formatter and continues;
- returns a specific failure code.

This is narrow and probably low-frequency, but it remains a real equivalence gap.

### L2-R3 — request-family / fallback census

The generic basename-oriented `OpenGameResource` branch is strong, but full Layer-2 closure requires proving the scope of all original resource-selection families rather than silently assuming every request uses this exact branch.

Audit all relevant callers/selectors for:

- missing-resource defaults;
- selector-specific fallback;
- resource-family-specific candidate changes;
- language/region alternatives;
- any branch that bypasses or modifies the generic twelve-attempt plan;
- container representation selection where packed-vs-`.lst` is part of choosing the logical representation.

Unknown families remain `UNRESOLVED`, not aliases of the generic resolver.

### L2-R4 — exact duplicate-key runtime observation if retail duplicates exist

Static evidence proves ambiguity of the semantic model, not a deterministic original winner. Only pursue exact duplicate winner behavior if real retail corpus proves such collisions exist in the claimed DMC3-HD scope.

Do not reverse this speculatively if the corpus census proves it non-operative.

## 4. L2 boundaries that are not current reverse blockers

Do not restart these without contradictory direct evidence:

- `0x14002E930` numbered-volume bootstrap core;
- mount prepend / effective archive `N..0` precedence;
- mounted-source resolver family around `0x140327430` at the already recovered precedence scope;
- `0x14002FCA0` basename + six-prefix + archive-pass/physical-pass core;

- exact-case existing file;

### L2-V4 — missing/default/fallback receipts

### L2-V5 — original-process selection receipt

## 7. Architecture risks

1. **Physical-provider laundering:** treating `LocalDirectorySource` or `product_physical_index` as original type-0 equivalence.
2. **Collision laundering:** calling deterministic product ambiguity the exact original CRT duplicate winner behavior.
3. **Namespace laundering:** inferring binary AFS from `GData*.afs/` strings.
4. **Generic-branch laundering:** assuming every DMC3 resource request is the `0x14002FCA0` generic branch without caller census.
5. **L1/L2 conflation:** successful materialization does not prove resolver equivalence, and a correct resolver does not prove byte materialization.
6. **Synthetic-to-runtime escalation:** #187 and unit tests establish product composition, not original-process dynamic selection.
