## 1. Scope and evidence class

This pass does not restart ZIP, physical-provider or PAC/PNST structural reverse. It re-reviews the weakest remaining handoff in the current L1 EXE model:

```text
materialization submission
 -> transport/read work
 -> scheduler ordering
 -> resource-level completion callback
 -> LoadedResource state 1 -> 2
```

No fresh raw canonical `e454...` executable blob was exposed through the connected file surface during this pass. Therefore this pass is a **fresh reconciliation of preserved direct canonical-disassembly authority**, not a claim of newly generated byte-level disassembly.

A focused guarded acquisition plan is added so the next run with the canonical executable can reacquire the exact neighborhoods required to test the remaining ordering/error questions.

## 2. Main correction — `fan-in counter` is not evidenced

The earlier shorthand **materialization fan-in/completion** is too strong if read as a claim that the original runtime owns an explicit child/outstanding-work counter.

Current preserved canonical evidence directly establishes:

- a lower FileSlot/ReadRequest transport layer;
- a higher scheduler ring with enqueue, worker and pending-entry clear/rollback helpers;
- successful materialization scheduling before `LoadedResource.state = 1` publication;
- a later resource-level scheduler callback that publishes normal `state 1 -> 2`;
- cancellation that clears/rolls back pending scheduler entries before marking unfinished records state 4 and queuing deferred cleanup.

Current evidence does **not** directly establish:

- an explicit child-count field;
- an outstanding-request counter used as a generic parent fan-in primitive;
- a generic `N children complete -> parent complete` counter transition;
- a universal aggregate object shared by packed/direct and `.lst` materialization.

Canonical wording after this pass is therefore:

> **materialization completion ordering / dependency barrier**

A fan-in counter may still exist, but it is **NOT EVIDENCED** and must not be encoded as recovered behavior until direct bytes/dataflow prove it.

## 3. Recovered scheduler structure

### `0x1402EF580` — scheduler enqueue

Preserved direct-disassembly authority establishes a scheduler-ring enqueue helper that:

- allocates/uses the next scheduler slot;
- publishes the pending/executable slot state;
- stores callback pointer and argument/context metadata;
- advances the ring.

This helper is used to register the `0x1401B8DC0` materialization completion callback and to queue deferred cleanup after cancellation.

### `0x1402EF790` — scheduler worker

The scheduler worker recognizes executable/pending entries, invokes the stored callback and clears the slot afterward.

This proves callback execution is mediated by a higher scheduler layer rather than by the raw FileSlot transport callback directly.

### `0x1402EF460` — pending scheduled-entry clear/rollback

Preserved direct evidence recovers this helper as pending scheduler-entry clear/rollback.

Safe label:

> **pending scheduled-entry clear/rollback**

It must not be relabeled as:

- `CancelIo`;
- OS AsyncIO cancellation;
- guaranteed cancellation of an already-running backend read;
- global FileSlot request cancellation.

Its recovered role is queue/scheduler rollback.

## 4. Forward materialization ordering

The strongest current generic sequence is:

```text
0x1401B84E0
  -> establish TypeInfo/payload destination
  -> 0x1401B8CA0 materialization dispatch
       -> direct/packed submission through 0x1402EF4D0
       -> or .lst synthesis through 0x1401B85C0
  -> only after successful materialization scheduling: state = 1
  -> register 0x1401B8DC0 through 0x1402EF580

scheduler worker 0x1402EF790
  -> invoke 0x1401B8DC0
  -> normal even record context resolves LoadedResource
  -> state = 2
```

This is enough to preserve the architectural fact that state 2 is a **resource-level materialization-complete handoff**, not transport completion itself.

It is not yet enough to prove why the completion callback cannot run before every byte/child dependency has finished. That exact dependency relationship is the central open question of this pass.

## 5. Transport completion remains a lower layer

The whole-file path remains independently recovered:

```text
0x140033500
 -> 0x14002EA40 transport submission
 -> FileSlot / ReadRequestV2
 -> backend read / NBZ STORE or InflateRead as selected
 -> 0x1400335A0(ticketId,userContext,errorFlag,bytesRead)
```

`0x1400335A0` updates whole-file transport progress/status. It is not the callback that publishes LoadedResource state 2.

Therefore the remaining bridge is specifically:

```text
transport status/progress
 -> materialization submission/scheduler state
 -> permission/order for 0x1401B8DC0
```

That bridge must be closed from exact dataflow, not inferred from two callbacks having completion-like roles.

## 6. Cancellation ordering is stronger than success-side dependency evidence

The canonical cancellation path gives a useful negative/control-side ordering receipt:

```text
0x1401B8430
 -> 0x1402EF460 pending scheduler-entry clear/rollback
 -> scan LoadedResource registry
 -> state 1|2 -> state 4
 -> enqueue 0x1401B8F00 through 0x1402EF580

0x1401B8F00
 -> deferred state4 cleanup
 -> state 0 + backing release
```

This proves the original manager does not merely mark state 4 and leave already queued higher-level scheduler work untouched. Pending scheduler entries are rolled back first.

It does **not** prove that already-running FileSlot/AsyncIO requests are synchronously cancelled by `0x1402EF460`. That remains a separate transport/cancellation question.

## 7. `.lst` consequence

`0x1401B85C0` constructs the parent container in-place and submits ordinary children / packed nested siblings through the generic materialization submission wrapper; nested loose lists recurse in-place.

The earlier phrase **child fan-in** is therefore replaced by the narrower question:

> What ordering/dependency mechanism guarantees that the parent materialization-complete callback is not published before all required `.lst` population work is valid?

Open possibilities include ordered synchronous work, scheduler dependency ordering, an unobserved counter/object, or another completion mechanism. None is promoted without exact evidence.

## 9. Exact questions for the next raw pass

The next canonical-byte run must answer, in order:

1. Does `0x1402EF4D0` itself enqueue one or more scheduler entries, call the whole-file loader, or select among multiple materialization modes?
2. What exact object/context is passed from `0x1402EF4D0` into any lower whole-file/FileSlot path?
3. What is the numeric domain and first concrete consumer of the inherited materialization/load-context parameter?
4. What exact queue insertion order exists between materialization work and `0x1401B8DC0` completion registration?
5. Is completion ordering guaranteed by ring order alone, by nested callbacks, by another status field, or by an explicit outstanding-work counter?
6. How does `0x1400335A0` transport failure reach the resource scheduler/materialization failure path?
7. On `.lst`, what prevents parent state2 publication after one ordinary child submission/population failure?
8. Which pending scheduler entries does `0x1402EF460` match and clear, and can it affect an already executing callback?
9. What happens to an already-running FileSlot/ReadRequest when higher scheduler rollback begins?
10. Which exact branches suppress `0x1401B8DC0` state2 publication after submit/read/materialization failure?
