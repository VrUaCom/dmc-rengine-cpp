# PTX: підготовка палітри, копіювання та контекст

Дата: 2026-09-16. Гілка: **Ада-Астра**. База проходу: `50d070e158e484937238d9cb02b2bc6affb2f502`.
Канонічний SHA-256 EXE: `e454272ed0fb0247fcbcf300e5d55d7a3e96d50b89b9ffaff81bb978dcbdd082`.

Відновлено C++ для `0x140331BD0`: дві схеми копіювання, лічильники,
таблиці та залежність від вхідного стану стеку. **232 сценарії EXE/C++ PASS;
обидва виходи всіх 10 conditional sites.** Дві перевірки host guards
враховано окремо. Це закриває зовнішню межу palette helper у
[placement-проході](dmc3-ptx-placement-2026-09-16.md), але не весь lifecycle
палітр і не графічний backend.

Оригінальні інструкції `0x140331BD0..0x140331D90` та wrapper
`0x14032D3D0..0x14032D3DB` виконуються в Unicorn. Wrapper зсуває `R8D`
вліво на 4 і переходить через IAT `0x14034F3F8` до
`VCRUNTIME140.dll!memmove`. Імпорт отримує адреси й **байтову** довжину;
його модель знімає байти джерела перед кожним записом. C++ bridge виконує
`std::memmove`. Сам palette helper і placement не підмінено.

Інтеграція виконує реальні materializer, allocator, placement, mark/unmark,
rollback, variant loader та операції кешу. Межами залишаються parser
`0x1403365B0`, render finalizer `0x140331A80` і перевірений CRT memset
80 байтів. Volatile GPR після модельованих зовнішніх викликів затираються.

## Префікс контексту та поля record

Аргумент `RDX` вказує на окремий контекст. Оригінальні назви класу й полів
невідомі; назви C++ описують підтверджений потік даних.

| Зсув контексту | Представлення | Підтверджена роль |
|---|---|---|
| `+0x00` | `uint64` | Адреса bank record для формату `0x13` |
| `+0x08` | `uint64` | Адреса bank record для формату `0x14` |
| `+0x10 / +0x12` | два `uint16` | Наступні автоматично виділювані індекси |
| `+0x14 / +0x16` | два `uint16` | Верхні межі unsigned-порівняння лічильників |
| `+0x18 / +0x38` | невідновлені підоб'єкти | Аргументи allocation/free helpers у статично досліджених lifecycle functions |

`PtxPaletteContextState` має розмір **0x18**, лише доведений префікс.
Це не розмір цілого оригінального класу. Тести також порівнюють незмінені
0x40 байтів після префіксу.

| Поле record | Використання |
|---|---|
| `+0x04`, `uint16` | Вибір гілки `0x13`, `0x14` або fallback |
| `+0x1A`, `int16` при перевірці | Від'ємне значення запускає автоматичне виділення індексу |
| `+0x28`, `uint64` | **Адреса призначення копіювання** |
| `+0x1E`, `uint16` | Обчислена база палітри, записується після всіх копіювань |
| bank record `+0x10`, `uint64` | Базова адреса джерела байтів |
| bank record `+0x06`, `int16` | База для обчислення вихідного `record+0x1E` |

Напрямок підтверджений викликами `0x140331C5C` і `0x140331CDC`:
destination береться з `record+0x28`, source — із bank record. Функція
копіює **з банку**, а не завантажує байти в нього.

## Автоматичний і заданий індекс

За `int16(record+0x1A) < 0` функція перевіряє
`uint16(next) >= uint16(capacity)`. Якщо так — повертає `AL=0` без змін
пам'яті. Інакше записує старий `next` у `record+0x1A`, збільшує лічильник
і лише потім копіює. Лічильник має 16-бітову ширину, але `0xFFFF` не може
пройти unsigned-перевірку за жодної 16-бітової capacity: успішний шлях
тут не обертає його через нуль.

Для невід'ємного `record+0x1A` capacity та increment пропускаються.
Підтверджена особливість: **індекс копіювання читається з
`word[ENTRY_RSP+8]`, а індекс вихідної бази — з `record+0x1A`.**
Ці значення можуть відрізнятися.

Пролог сумарно віднімає `0x38` від RSP. Інструкції `0x140331C18` і
`0x140331C95` читають `[RSP+0x40]`, тобто початковий `RSP+8`. Пролог
зберігає RBX/RBP за початковими `+0x10/+0x18`, але не записує слово `+8`.
У C++ це явний `incoming_home_word`: вхідний машинний стан, а не вигаданий
третій параметр оригінальної функції. Тести задають початковий стек до
виконання інструкцій і перевіряють його фактичне значення на вході helper,
у тому числі через materializer.

За інших форматів копіювань та доступів до bank record немає. Інструкція
`0x140331D73` читає dword із того самого місця стеку, його молодше слово
потрапляє в `record+0x1E`, функція повертає `AL=1`. Цю поведінку збережено;
fallback не замінено нулем або помилкою.

## Копіювання й таблиці

Нехай `i` — signed 16-бітовий індекс копіювання, `S` — bank record `+0x10`,
`D` — record `+0x28`. Ділення усікається до нуля; залишок має знак діленого.
Додавання до адрес зберігає 64-бітове обертання.

| Формат | Перша source-адреса | Послідовність memmove |
|---|---|---|
| `0x14` | `S + (i / 8) * 2048 + (i % 8) * 32` | 2 копії по 32 байти; source `+256`, destination `+32` |
| `0x13` | `S + (i / 4) * 4096 + (i % 4) * 64` | 16 копій по 64 байти; source `+256`, destination `+64` |

Це **64 або 1024 байти призначення**, але джерело читається окремими
ділянками зі stride 256. Цикл не еквівалентний одному суцільному
копіюванню. Overlap усередині одного буфера перевірено окремо: наступний
memmove бачить попередні записи.

Після копіювання `j = int16(record+0x1A)`, `B = int16(bank_record+6)`:

| Формат | Значення до усічення до 16 біт | Таблиця |
|---|---|---|
| `0x14` | `B + (j / 32) * 32 + int8(T14[j % 32])` | `0x1405D16F0`, 32 номінальні записи |
| `0x13` | `B + (j / 8) * 32 + int8(T13[j % 8])` | `0x1405D1710`, 8 номінальних записів |

Номінальні таблиці, десяткова нотація:

```text
T14 = 0,1,4,5,16,17,20,21,2,3,6,7,18,19,22,23,
      8,9,12,13,24,25,28,29,10,11,14,15,26,27,30,31
T13 = 0,4,16,20,8,12,24,28
```

Автоматичний лічильник перевіряється як unsigned, потім перетворюється на
signed word. Значення від `0x8000` можуть тому читати **байти перед
номінальною таблицею**. C++ зберігає 31 попередній байт T14 та 7 попередніх
байтів T13 канонічного EXE; їхні адреси, вміст і хеші наведено в evidence.
Це не розширення семантичних меж таблиць. Перевірено від'ємні залишки,
signed base та усічення вихідного слова. Числа форматів не прирівняно до
конкретного GPU-формату без дослідження backend.

## Failure paths і caller state

| Сценарій | Підтверджений залишковий стан |
|---|---|
| Capacity вичерпана | Helper не змінює пам'ять; materializer уже міг зарезервувати поточний record |
| Після копіювання placement повертає 0 | Materializer звільняє record; palette counter і destination залишаються зміненими |
| Палітра другої текстури не проходить capacity | Outer loader звільняє records попередньої текстури; поточний record залишається зарезервованим; counter не зменшується |
| Повторне отримання ключа кешу | Palette helper не викликається, навіть через інший варіант acquire |
| Release до нуля, потім повторне завантаження | Records очищуються, counter не повертається; нове завантаження бере наступні індекси |

У failure-сценаріях перевірено return code, порядок копіювання, звільнення
record і збереження counter/destination. Це локальна поведінка ланцюжка,
**не доказ постійного витоку ресурсів гри**: контекст має окремий cleanup.

## Статичні шляхи життєвого циклу

Ці докази позначені `STATIC_ONLY_NOT_DIFFERENTIALLY_EXECUTED`:

- `0x140331180` готує до двох bank records із глобального пулу, викликає
  placement, mark та `0x1402C6150` для підоб'єктів `+0x18/+0x38`;
  встановлює bank pointers, next і capacity.
- `0x140331460` проходить два bank pointers, за відповідних умов очищує
  occupancy та record, обнуляє pointer/next/capacity й викликає
  `0x1402C6260` для відповідного підоб'єкта.
- `0x1402C0594` викликає initializer для **глобального контексту
  `0x140CF1030`** з `EDX=16`, `R8D=32`. Це конкретна гілка caller,
  а не універсальні live limits усіх контекстів.
- `0x1402C035B` передає той самий глобальний контекст у cleanup.
- `0x140245D67` передає `this+0x5E0` у cleanup, якщо byte `this+0x638`
  ненульовий. Тип власника та повний шлях створення відкриті.

Call sites повторно перевірено за EXE; їхні байти й відповідні фрагменти
caller збережено. Список не претендує на повноту непрямих або ще не
охоплених викликів. Підоб'єкти allocation helpers ще не відновлені як класи.

## Відтворення й невідоме

Потрібні Python, Capstone 5, Unicorn 2 та компілятор C++20. Із кореня репозиторію:

```sh
python scripts/reverse/verify_ptx_palette.py /path/to/dmc3.exe . data/reverse/ptx-palette-20260916
```

Скрипт перевіряє SHA-256 EXE, компілює C++ з `-Wall -Wextra -Wconversion
-Werror`, порівнює повні області pool/payload/manager/input/source/context,
три буфери даних, profile, 64-байтові guards, return values і порядок подій.
Fixture source/input не перетинаються з writable palette buffers: їх
незмінність не доводить, що справжній parser ніколи не повертає destination
усередині source bundle.

Host guards відкидають bank pointers/copy ranges поза представленою
пам'яттю. Їхні винятки не є оригінальними `AL=0` або Windows SEH. Не
перевірялися aliasing з pool/context, concurrency та графічне виконання.

Далі: C++ та EXE-перевірка initializer/cleanup контексту
`0x140331180 / 0x140331460` і allocation helpers, зокрема partial failures.
Потім caller lifecycle глобального й embedded контекстів, finalizer
`0x140331A80`, parser `0x1403365B0` та зв'язки з draw/shutdown. Структурні
прогалини vtable/CRT зберігаються в [черзі гілки](ada-astra-reverse-queue.md).
