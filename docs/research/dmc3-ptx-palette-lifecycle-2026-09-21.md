# PTX: життєвий цикл палітр і спільний блочний алокатор

Дата: 2026-09-21. Гілка: **Ада-Астра**.
База: `7a3b811bdb8ad33dc0fd8ded81f2895d8acb1575`.
Канонічний EXE SHA-256: `e454272ed0fb0247fcbcf300e5d55d7a3e96d50b89b9ffaff81bb978dcbdd082`.

**Результат: 310 сценаріїв EXE/C++ PASS.** Відновлено створення й очищення
контексту палітр, вибір арени пам'яті, пошук вільної ділянки та
виділення/звільнення блоків. Обидва виходи перевірено для 44 із 49 умовних
інструкцій; решта п'ять належать до dispatch за форматом, який initializer
перед цим завжди встановлює в нуль. Дві перевірки host guards рахуються окремо.

**Оновлення 2026-09-23:** callback acquire/enqueue/drain/recycle та arena
initializer `0x140337780` тепер мають окрему EXE/C++ перевірку на 10
сценаріях. Синтетична межа callback drain, описана нижче, знята; фактична
поведінка callback-вузлів підтверджена в межах нового звіту
[PTX callback та arena initialization](dmc3-ptx-callback-arena-2026-09-23.md).
Backing allocator `0x140337920` та порядок викликів власників ще відкриті.

Це продовження [обробника палітр](dmc3-ptx-palette-2026-09-16.md).
Результати мають статус **EXE_CONFIRMED у зазначеній області перевірки**.
Тіла callback-цілей, backing allocator, і порядок викликів життєвого циклу
у грі залишаються відкритими.

## Структури й володіння

Контекст палітр має представлений діапазон **0x58**:
префікс 0x18 із bank pointers/next/capacity та два записи виділення по 0x20
за `+0x18/+0x38`. Це обґрунтований memory view; оригінальні назви класів
і їхні повні декларації не встановлені.

| Поле `BlockAllocationState` | Тип | Підтверджена роль |
|---|---|---|
| `+0x00` | `uint64` | Голова callback-списку для `0x1403292A0` |
| `+0x08` | `uint64` | Адреса арени або нуль |
| `+0x10` | `uint64` | Адреса виділених даних |
| `+0x18` | `int32` | Початковий індекс блока; reset значення `-1` |
| `+0x1C` | `uint32` | Кількість блоків |

| Поле `BlockArenaState` | Тип | Підтверджена роль |
|---|---|---|
| `+0x00` | `uint64` | Адреса побайтової карти зайнятості |
| `+0x08` | `uint64` | База даних арени |
| `+0x10` | `int32` | Межа сканування карти в блоках |
| `+0x14` | `uint32` | Кількість байтів у блоці |
| `+0x18` | `uint32` | Умова доступності: виділення вимагає ненульового значення |
| `+0x1C` | `uint32` | Збережено без приписування семантики |
| `+0x20` | `uint32` | Лічильник активних виділень |
| `+0x24` | `uint32` | Збережено без приписування семантики |

Таблиця арен адресується від `0x140CA8910` із кроком **0x28**.
Три арени в harness — представлена область тесту, не доказ розміру
глобального масиву. Оригінальний router не перевіряє діапазон індексу.
Алокатор спільний: прив'язувати його тип лише до PTX підстав немає.

## Створення банків

Для кожного з двох count initializer окремо виконує:

1. Якщо signed count `<= 0`, пропускає банк, **не очищуючи його старий стан**.
2. Резервує перший record пулу з word `+0 == 0`.
3. Встановлює format `+4 = 0`, width `+0x0A = 64`, `+8 = 1`,
   palette marker `+0x1C = -1`, `+0x44 = 0`, dword `+0x18 = 0`.
4. Обчислює height, викликає реальні placement `(0,0)` і mark.
5. Публікує bank pointer у контексті, встановлює next=0 і low16(count) capacity.
6. Виділяє дані через відповідний handle, router mode=1; записує результат
   у record `+0x10`, включно з нулем при відмові.
7. За ненульової адреси повторно обнуляє буфер через `0x14032D3C0`.

Для першого банку groups = `trunc_zero(signed32(wrap32(count+7))/8)`,
для другого — `trunc_zero(signed32(wrap32(count+31))/32)`.
Height дорівнює low16(groups*32). Розмір виділення —
`wrap32(64 * int16(height) * 4)`. Отже, звичайне математичне округлення
без збереження ширини й знаку не відтворює великі count. Граничні значення
перевірено на EXE, включно з нульовим/від'ємним height після усічення.

Dispatch множника розміру містить гілки інших форматів, але `+4` завжди
встановлено в нуль до реальних placement/mark, які його не змінюють.
За неаліасного стану доступна тільки гілка множення на 4. Невиконані
альтернативи п'яти conditional sites явно перелічені в receipt; покриття
не оголошено 49/49. Інші байти record зберігаються до явного запису або clear.

## Вибір арени й виділення

Router читає byte `0x140CA8AB2` для дозволу fallback та
byte `0x140CA8AB1` для спеціального вибору арени.

| Умова | Поведінка |
|---|---|
| Force-byte рівно `1` | Обирає індекс 2 |
| Інакше mode `-2` | Обирає індекс 1 |
| Інакше mode `-1` | Signed32(bytes) `<= 1024` обирає 1, інакше 0 |
| Інший mode | Використовує сам індекс |

Дозвіл повторної спроби обчислюється **до** перетворення mode:
fallback-byte ненульовий і початковий mode ненульовий. Після першої
відмови 0 змінюється на 1, 1 — на 0, інші індекси залишаються тими самими.
Тому forced arena 2 може бути перевірена двічі, а початковий mode=0
забороняє fallback навіть із forced arena 2. Це підтверджено записом
фактичних викликів `0x140337600`.

Саме виділення повертає нуль без змін за bytes=0, arena=null,
arena.data=null, availability_gate=0 або вже зайнятого handle (`arena != 0`).
Далі воно обчислює unsigned ceil(bytes/block_bytes), прив'язує handle до
арени й викликає пошук. При `first=-1` відв'язує arena, але **зберігає старі
data, blocks і callback_head**. При успіху:

- записує blocks і заповнює відповідні байти карти значенням `1`;
- збільшує live_allocations з uint32-обертанням;
- обчислює data = arena.data + `wrap32(block_bytes * first)`;
- обнуляє саме запитані bytes, а не всю округлену місткість блоків.

## Пошук вільного місця

Карта має починатися за адресою, кратною восьми, інакше пошук повертає `-1`.
Префікс сканується групами по вісім: qword `0x0101010101010101` швидко
пропускається. В іншій групі шукається перший **нульовий** байт. Якщо його
немає, функція одразу повертає `-1`, навіть коли пізніше є вільне місце.

Після знайденого нуля всередині пробної ділянки зайнятим вважається лише
байт, рівний `1`. Хвіст карти теж використовує порівняння з `1`.
Отже, для `2` або `255` поведінка залежить від місця входу в алгоритм.
Ці випадки відтворено; карту не нормалізовано до загального правила
«ненульове означає зайняте». Лічильник пройдених вільних байтів, що
керує поверненням до групового сканування, не скидається на кожній перешкоді.

## Очищення та відмови

Очищення контексту для кожного банку звільняє допустимий record, обнуляє
bank pointer/next/capacity, потім звільняє handle. Перевірка record включає
обидві межі пулу й **не перевіряє вирівнювання**. Cleanup handle викликається
навіть при null/недопустимому bank pointer.

За ненульової arena звільнення handle спершу обнуляє карту зайнятості,
зменшує live_allocations, потім викликає `0x1403292A0`. На момент callback
handle ще містить arena/data/first/blocks. Лише після нього поля скидаються.
Дані арени не стираються. За arena=null callback drain не викликається,
callback_head зберігається, а решта полів скидається. Повернення цього
helper — `AL=1/0` залежно від наявності арени на вході.

| Відмова або послідовність | Стан після подальшого cleanup контексту |
|---|---|
| Вичерпано records до резервування наступного | Уже прив'язані банки очищуються |
| Placement відмовив після резервування record | Новий record ще не прив'язаний до контексту й залишається в пулі |
| Виділення data відмовило після placement/mark | Record уже прив'язаний; cleanup очищує його та occupancy |
| Повторний initializer на живому контексті | Новий bank pointer записується до перевірки busy handle; старий record може втратити зв'язок із контекстом |
| Initialize → palette copy → cleanup → cleanup → initialize | Перевірена послідовність завершується узгодженим станом |

В окремому сценарії повторної ініціалізації record 0 лишається зайнятим,
а records 1 і 2 прибираються подальшим cleanup. Це встановлена поведінка
зазначених функцій, не доказ того, що реальний caller порушує порядок
життєвого циклу або гра має постійний витік.

## Межі перевірки й наступна робота

EXE виконує всі наведені операції, а також уже відновлені placement,
mark/unmark і palette copy. Перехоплено CRT memset/memmove та
**`0x1403292A0`**: модель drain фіксує стан на вході й синтетично обнуляє
callback_head. Вона не відтворює виклики конкретних callback-ів або
повернення вузлів у глобальний вільний список. Це наступна відкрита залежність.

Порівнюються повні pool/context/arena/map/data/profile/destination області,
64-байтові guards, визначені return values, порядок memory/callback подій
і знімки context/arena перед ними; для fill/drain також хеш pool,
для memmove — хеш джерела.
Cleanup контексту сам не встановлює
окремого return value: C++ API має void, випадковий регістровий залишок
цієї функції не прирівнюється до семантичного результату.

Арени ініціалізуються явними fixtures. Не перевірені production arena setup,
реентерабельні callback-и, concurrency, aliasing metadata/буферів, Windows
SEH і графічне виконання. Host guards для нульового block_bytes та виходу
за представлені арени не є оригінальними перевірками EXE.

Відтворення з кореня репозиторію, Python + Capstone 5 + Unicorn 2 + C++20:

```sh
python scripts/reverse/verify_ptx_palette_lifecycle.py /path/to/dmc3.exe . data/reverse/ptx-palette-lifecycle-20260921
```

Callback queue, backing allocator та їхні окремі звіти додані після цього
історичного проходу. Реальний initialize/cleanup порядок глобального контексту
`0x140CF1030` й embedded `this+0x5E0` ще не з'єднаний спільним runtime trace.
Bounded static pass для finalizer `0x140331A80` є в окремому звіті; registry
consumers, parser і зв'язки з draw/shutdown ще відкриті.
Структурні прогалини CRT/vtable залишаються в [черзі гілки](ada-astra-reverse-queue.md).
