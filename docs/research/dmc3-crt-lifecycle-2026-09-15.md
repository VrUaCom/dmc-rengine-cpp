# DMC3 — CRT, глобальні об'єкти та межі vtable

Гілка: **Ада-Астра**. Дата: 2026-09-15.
EXE SHA-256: `e454272ed0fb0247fcbcf300e5d55d7a3e96d50b89b9ffaff81bb978dcbdd082`.
Батьківський коміт: `9b63f338b2daca9dc9f3fbf8895bc351f2380427`.

## Перевірений результат

Відновлено перерваний `root-pass/`, а потім виконано новий прохід по
повних локальних тілах 83 CRT-входів, які раніше класифікувалися лише за
префіксом. Реалізовано на C++ два цикли ініціалізації глобальних масивів;
їхні операції з пам'яттю перевірено виконанням оригінальних інструкцій EXE
в Unicorn. Це конкретні відновлені фрагменти поведінки, не завершена гра.

| Аспект | Результат | Межа доказу |
|---|---:|---|
| CRT-входи з переходами | 83 тіла | Без рекурсивного відновлення всіх callees |
| Реєстрації cleanup | 71 адреса / 71 callback | Реєстрація не доводить успішного запуску чи повного destructor |
| Callback з одним `ret` | 40 | Нуль операцій з глобальною пам'яттю |
| Прямі виклики array-construction helper з CRT | 11 | Збережено base, stride, count, callback і п'ятий аргумент |
| Перевірені caller paths | 79 прикладних входів, 143 transfer sites | Callees замінено визначеними заглушками |
| Перевірені прикладні cleanup-прив'язки | 69 | Дві інші належать CRT platform paths |
| C++ проти EXE | 24 випадки, усі PASS | Два ініціалізатори; сервіс реєстрації перехоплено |

### Реєстрація завершення

`0x1403458D0` викликає `0x140345880`. У ньому за станом CRT вибирається
`0x140346C86 → IAT 0x14034F570 → _crt_atexit` або
`0x140346C80 → IAT 0x14034F588 → _register_onexit_function`.
Переданий callback зберігається через RBX. Внутрішня політика зберігання та
виконання списку належить CRT; загальний порядок shutdown гри тут не закритий.

З 71 відновленої callback-адреси **40 ведуть лише на `ret`**, інші 31 мають
додатковий код або tail-transfer. Не можна перетворювати всі 71 записи на
71 власника ресурсів чи 71 нетривіальний деструктор.

## Зв'язки глобальних об'єктів

| Об'єкт | Ініціалізація | Cleanup | Що уточнено |
|---|---|---|---|
| `CMcAppli` у `0x140CF3310` | `0x140023E10`, vptr `0x140508728` | Зареєстровано `0x14034EB80` | Підоб'єкти `+0x288`, `+0x2B0` ініціалізуються в цьому порядку; cleanup передає їх у зворотному |
| `CPtxManager` у `0x140D5B860` | `0x140025050 → 0x140314C50` | `0x14034ECA0 → 0x140314D00` | Vptr `0x140507B60`; 32 елементи зі stride `0x218`; після cleanup vptr бази `IPtxManager`, `0x140507B30` |

Для CMcAppli виклики `0x140329200`, потім `0x1403376F0` отримують
`0x140CF3598` і `0x140CF35C0`. Cleanup викликає `0x140337440` спочатку
для `0x140CF35C0`, потім для `0x140CF3598`. Типи членів і повна семантика
цих helpers ще не відновлені. Історичний `0x1403295B0` є окремим
deleting-destructor шляхом; CRT callback має іншу адресу.

У CPtxManager constructor sites `0x140314C87/0x140314C8C` передають
stride `0x218`, count `32`; `0x140314C92` викликає `0x140345B24`.
Cleanup sites `0x140314D27/0x140314D2C/0x140314D32` передають ті самі
stride/count до `0x140345B94`. Ці аргументи й записи vptr перевіряються
скриптом, але в цьому проході весь CPtxManager не перенесений на C++.

Це продовження [історичної карти адрес Drive](https://docs.google.com/document/d/1KdmzRsvQVAefpmi54zqaDRtz5SfaHTPuwdFjs3Sih-0/edit)
(прочитано 2026-09-15; last modified 2026-08-04). Імена та globals звірено
з EXE/RTTI; історичні твердження про всю підсистему автоматично не підвищувалися.

## Дві реалізації C++

Файли: `include/dmc_rengine/reverse/crt_global_initializers.hpp` та
`src/reverse/crt_global_initializers.cpp`; namespace `dmc::rengine::reverse`.
Нейтральні назви з адрес зберігають невизначеність прикладного призначення.

### `0x140021A20` — банк 768 записів

Область `[0x140CB9ED0, 0x140CBCED0)`, stride `0x10`.
Цикл `0x140021A40..0x140021A4E` записує `u16 = 0xFFFF` у `+0x00`
та `u64 = 0` у `+0x08`; **шість байтів `+0x02..+0x07` не змінюються**.
Потім реєструє callback `0x14034EA50`, який лише повертається.
Не доведено, що `u64` є вказівником або що `u16` є ID.

### `0x1400236A0` — два набори по 16 елементів

У `0x140CF2D90` — 16 dword зі значенням `0x3F800000` (біти `1.0f`).
У `0x140CF2E10` — 16 записів зі stride 8: dword у `+0x00` дорівнює
`0x3F800000`, byte у `+0x04` дорівнює нулю. Три байти `+0x05..+0x07`
зберігаються. Окремо обнуляється byte `0x140CF2E90`, потім реєструється
порожній callback `0x14034EB50`. Проміжок `0x40` між масивами не змінюється.

Реалізації не підставляють ці адреси як callable host-покажчики і не
запускають Windows EXE. Вони відновлюють конкретні операції на переданій
типізованій пам'яті та викликають переданий сервіс реєстрації.

### Перевірка поведінки

24 випадки: два ініціалізатори × шість початкових буферів (нулі, `FF`,
`A5`, три детерміновані випадкові набори) × return status реєстрації `0/-1`.
Порівняно всі байти, включно з невідомими полями, проміжком та 64-байтовими
guard-областями. Перевірено один callback, записи до реєстрації, точну кількість
EXE stores (1536 / 49), повторну C++-ініціалізацію й відсутність memory effects
у cleanup. Компіляція: C++20, GCC 13.3, `-O2 -Wall -Wextra -Werror`.

Додатково Unicorn пройшов 79 прикладних CRT caller bodies із заглушками
замість callees; заглушки змінюють усі volatile GPR. Зіставлено 143 transfer
sites, усі 69 прикладних cleanup-прив'язок і 11 array-helper викликів.
Це перевірка відновлення аргументів, **не тест справжніх конструкторів**.
Чотири CRT platform bodies залишаються лише статично каталогізованими.

## Три довгі послідовності vtable

| RTTI-клас | Anchor | Кількість code pointers | Кінець, не включно |
|---|---|---:|---|
| `CComEm000` | `0x1404C6A18` | 256 | `0x1404C7218` |
| `CComEm006` | `0x1404C75E0` | 262 | `0x1404C7E10` |
| `CComEm008` | `0x1404C7EA0` | 262 | `0x1404C86D0` |

Кінець кожної послідовності — slot наступного перевіреного RTTI locator.
Для CComEm000 старий ліміт 256 точно збігся з фізичною межею; для двох
інших він приховав по шість записів. Загалом тепер **13 894 кандидатні
slots / 3315 унікальних targets**. Усі 12 доданих slots ведуть у вже
охоплений код, тому **899 неохоплених унікальних кандидатів залишаються**.

Перевірено дев'ять записів цих primary vptr у коді та три secondary
adjustor thunks: `this -= 0xD0`, далі jump до першого entry primary table.
Зсув узгоджується з RTTI subobject offset 208. Адреси записів і thunks
збережено окремими JSON. Фізична межа code-pointer run встановлена;
точна семантична довжина кожної C++ vtable та ABI всіх методів ще відкриті.

## Відтворення

Запускати без `python -O`: перевірки канонічних інструкцій використовують `assert`.
Залежності: Capstone 5.0.7; для виконуваної перевірки Unicorn 2.1.4 і g++.
З кореня репозиторію:

```sh
python scripts/reverse/audit_crt_lifecycle.py /path/to/dmc3.exe . data/reverse/crt-lifecycle-20260915
python scripts/reverse/audit_vtable_boundaries.py /path/to/dmc3.exe . data/reverse/vtable-boundaries-20260915
python scripts/reverse/verify_crt_lifecycle.py /path/to/dmc3.exe . data/reverse/crt-lifecycle-20260915/verification.json
```

Скрипти перевіряють SHA-256 до аналізу. Вихід містить повні адресні списки
інструкцій тіл, переходи, відновлені локальні аргументи, відомі записи,
callback-прив'язки, результати перевірки й хеші джерел C++.
В EXE не вносяться зміни; EXE та raw disassembly не додаються до репозиторію.

## Наступний пріоритет і невідоме

1. Розібрати 31 непорожній cleanup і відповідні callees; окремо уточнити
   exception rollback у array helpers та чотири platform CRT roots.
2. Продовжити CPtxManager і CMcAppli від підтверджених globals до типів
   членів, користувачів, ownership та initialize/update/draw/shutdown.
3. Підтвердити typed slot consumers довгих CComEm tables, призначення
   слотів 256–261 та решти 899 неохоплених кандидатних адрес.
4. Повнота non-RTTI classes, callbacks, indirect dispatch та загальний
   порядок shutdown лишаються OPEN. Відсоток повноти реверсу не визначено.
