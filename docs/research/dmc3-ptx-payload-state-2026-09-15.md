# DMC3 — завантаження PTX і життєвий цикл записів пулу

Дата: 2026-09-15. Гілка: **Ада-Астра**.
База: `284d580c1587831a1aa51fa61fe1b7795cc29d12`.
Канонічний EXE SHA-256:
`e454272ed0fb0247fcbcf300e5d55d7a3e96d50b89b9ffaff81bb978dcbdd082`.

## Результат

Наступний крок після [кешу CPtxManager](dmc3-ptx-manager-state-2026-09-15.md):
на C++ відновлено обидва завантажувачі bundle, резервування запису пулу,
очищення його ділянок, звільнення запису та всього payload. Статус описаної
нижче поведінки — **EXE_CONFIRMED** у зазначених межах.

**79 диференційних сценаріїв — PASS**: виконуються оригінальні інструкції,
порівнюються результати, вся представлена пам'ять та порядок зовнішніх
викликів. Три окремі перевірки захисних умов C++ не зараховані до паритету EXE.

Реалізація: `include/dmc_rengine/reverse/ptx_payload_state.hpp`,
`src/reverse/ptx_payload_state.cpp`. Вони входять у Core через наявний
`GLOB_RECURSE src/*.cpp`; окрема реєстрація CMake не потрібна.
Тестовий міст також зв'язує нові функції з реалізацією `CPtxManager`.

## Представлення стану

Це структури пам'яті процесу, не новий файловий формат PTX.

| Поле payload | Значення | Доказ |
|---|---|---|
| `+0x000..+0x1FF` | 64 слоти по 8 байтів з адресами записів пулу | копіювання `0x140336C70..0x140336C87`, cleanup `0x140331823` |
| `+0x200` | кількість успішно доданих текстур | increment `0x140336C2D`; product у cleanup |
| `+0x204` | кількість записів від першої текстури | `0x140336C33..0x140336C3D` |

`PtxPayloadState` має розмір `0x208`. Сумісність із попереднім opaque
`PtxPayload` забезпечують `decode_ptx_payload_state` / `encode_ptx_payload_state`.
Адреси записів — дані канонічного адресного простору, не callable host pointers.

| Пул і scratch | Адреса / розмір |
|---|---|
| Перший запис | `0x140D5FB70` |
| Кількість / stride | 128 / `0x50` |
| Останній допустимий початок запису | `0x140D62320`, включно |
| Початок карти зайнятості | pool `+0x2800` |
| Базові одиниці адресації | signed dword pool `+0xCB08` |
| Поточна кількість матеріалізованих записів | dword `0x140D6C690` = pool `+0xCB20` |
| Чотири scratch-посилання | `0x140D6C698` = pool `+0xCB28` |

Розмір `PtxPoolImage = 0xCB48` — обсяг пам'яті, представлений цим проходом,
не твердження про повний розмір оригінального класу. Невстановлені байти
зберігаються. Облік render descriptors і додаткові поля пулу ще відкриті.

## Алгоритми завантаження

`0x140336BB0` і `0x140336A70` читають signed count із source `+0`, таблицю
блоків із `+4` і починають із source `+0x800`. Для кожної текстури:

1. `0x1403365B0(source, descriptor)` готує 64-байтовий опис.
2. `0x1403366E0(descriptor, -1, argument)` матеріалізує записи.
   Basic loader передає нуль; variant передає незмінені 64 біти аргументу.
3. Після ненульових результатів обох викликів збільшується payload `+0x200`.
4. На першій ітерації scratch count копіюється в payload `+0x204` і локальну
   змінну. Наступні scratch counts **не змінюють** ширину копіювання.
5. Посилання копіюються за індексом `texture_index * first_count + j`.
6. Курсор джерела просувається на `uint32(block_count << 11)`. Старші біти
   губляться до додавання до 64-бітної адреси; це перевірено в емуляторі.

Після циклу викликається `0x140331A80(payload)`; його результат повертається
далі. Нульовий або від'ємний source count теж доходить до цієї функції,
зберігаючи попередні байти payload. Сам loader не обнуляє payload на вході;
при роботі через `CPtxManager` це робить код кешу перед викликом.

При нульовому результаті parser або materializer викликається
`0x1403317D0(payload)`, після чого loader повертає 0. Очищення проходить лише
слоти, уже включені в payload. Scratch-результат поточної невдалої ітерації
не копіюється: його повний rollback треба доводити всередині materializer.
У `0x1403366E0` статично видно різні виходи помилки, зокрема прямий вихід
при невдалому резервуванні. Це відкрита задача, а не доведена відсутність витоків.

Дескриптор на стеку повторно використовується без початкового memset.
`PtxLoadWorkspace` робить його початкові байти явним входом моделі;
перевірка використовує ненульовий шаблон і parser, що змінює лише частину полів.

## Резервування та очищення

`0x1403313F0` шукає перший із 128 записів із нульовим word `+0`.
Встановлює word `+0 = 1`, word `+2 = index`, повертає адресу запису.
Інші 76 байтів залишаються без змін. Якщо пул зайнятий, результат — null.

`0x140331420` і розгорнутий варіант усередині `0x1403317D0`:

- ігнорують null та адреси поза включним діапазоном першого/останнього запису;
- **не перевіряють вирівнювання** адреси на stride `0x50`;
- при word `+0x46 != 0` викликають `0x140330F60` для карти зайнятості;
- обнуляють усі `0x50` байтів через `0x14032D3C0(record, 0x14)`;
  цей wrapper множить довжину на 4 і передає її імпортованому `memset`.

`0x140330F60` очищає карту за формулою:

`pool + 0x2800 + trunc_toward_zero((int16(record[+6]) - int32(pool[+0xCB08])) / 32)`.

Віднімання має 32-бітну wrap-поведінку; signed довжина взята з record `+0x0E`.
Друга ділянка використовує record `+0x1E/+0x26` лише якщо signed word
`+0x1C >= 0`, word `+0x18 == 0` і word `+0x44 == 0`. Її роль як palette
allocation є **SEMANTIC_CANDIDATE**; умови й операції з байтами підтверджені.

Цикли очищення — do-while. Довжина 0 не означає «нічого не робити»:
після першого запису лічильник стає `0xFFFFFFFF`. C++ відхиляє нульові й
від'ємні довжини як вихід за межі представленої нормальної поведінки.
Це додана захисна умова, не властивість EXE й не Windows SEH.

Payload cleanup використовує signed молодші 32 біти добутку двох лічильників,
перечитує його на кожній ітерації, потім обнуляє всі 520 байтів payload.
Дублікати посилань не усуваються. Прямих викликів GPU destructor у цих
функціях немає; відновлено очищення пулу й карти зайнятості.

## Перевірка та її межі

```sh
python scripts/reverse/verify_ptx_payload.py /path/to/dmc3.exe . data/reverse/ptx-payload-state-20260915
```

Залежності: Capstone 5.0.7, Unicorn 2.1.4, g++ із C++20. Компіляція:
`-O2 -Wall -Wextra -Wconversion -Werror`.

Порівнюються всі `0xCB48` байтів пулу, 520 байтів payload, 64 байти
workspace, `0x4308` байтів manager, незмінність source та 64-байтові guards.
Сценарії включають усі 64 слоти, перший/останній/відсутній вільний запис,
нульові й невалідні адреси, невирівняну адресу, дублікати, gates другої
ділянки, від'ємні зміщення й округлення ділення, wrap добутку/зсуву,
помилки на різних ітераціях і повний cache → load → release ланцюг.

Оригінальні loader, cache, allocation, release і cookie-check виконуються
без заміни інструкцій. Межі з тестовою поведінкою: parser `0x1403365B0`,
materializer `0x1403366E0`, finalizer `0x140331A80` та CRT memset із перевіреним
80-байтовим контрактом. Ці межі прямо записані у `verification.json`.
Змінні scratch counts перевіряють механіку loader; їх сумісність із
реальним finalizer не заявляється. Той розіменовує отримані записи.

Host guards для виходу за memory view або неправильних довжин не гарантують
rollback попередніх змін. Aliasing між окремими структурами, reentrancy,
concurrency, Windows exception unwinding і GPU acceptance не перевірені.

`evidence.json` містить адреси й хеші тіл у явно визначених вікнах.
Враховано chained `.pdata`: перший RUNTIME_FUNCTION не є повним тілом,
наприклад у `0x1403317D0`. Лічба інструкцій не є оцінкою повноти реверсу.

## Наступні задачі

1. `0x1403366E0`: відновити матеріалізацію `0x50`-байтових записів,
   додатковий аргумент, `0x140331520/0x1403310F0` і всі шляхи rollback.
2. `0x140331A80`: побудова render descriptor і зв'язок з
   `0x14032D6B0/0x140033370`, полями record `+0x30..+0x40`.
3. `0x1403365B0`: окремо довести TM2 і non-TM2 backend.
   [Попередня перевірка companion](dmc3-model-texture-companion-framing-2026-09-13.md)
   вже встановила descriptor+DDS у retail corpus; вимогу TM2 для всіх
   ресурсів повертати не можна. Нового corpus-проходу тут не було.
