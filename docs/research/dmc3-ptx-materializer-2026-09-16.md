# DMC3 — матеріалізація PTX та залишковий стан після помилки

Дата: 2026-09-16. Гілка: **Ада-Астра**.
База: `8e6ed6a98d851bfe661e245b73c14ea048cdae2b`.
EXE SHA-256: `e454272ed0fb0247fcbcf300e5d55d7a3e96d50b89b9ffaff81bb978dcbdd082`.

## Перевірений результат

Відновлено на C++ `0x1403366E0` — створення проміжних записів текстури —
та `0x1403310F0` — позначення зайнятих ділянок. **71 диференційний сценарій
PASS**, додатково 3 host guards, які не зараховані до паритету EXE.

Головне нове спостереження: помилки матеріалізації мають різний rollback.
Нестача вільних записів і відмова palette helper повертають 0 без очищення
поточного scratch-набору. Відмова placement helper звільняє цей набір.
Для реального вичерпання пулу перевірено весь виклик від `CPtxManager`:
зовнішнє очищення прибирає попередні завершені текстури, але не незавершену
поточну. Це **EXE_CONFIRMED** у межах дослідженого ланцюга, не твердження
про неможливість подальшого global/scene reset.

Реалізація: `include/dmc_rengine/reverse/ptx_record_materializer.hpp`,
`src/reverse/ptx_record_materializer.cpp`. Вона використовує вже перевірені
[loader/pool functions](dmc3-ptx-payload-state-2026-09-15.md), а через тестовий
міст — також [кеш CPtxManager](dmc3-ptx-manager-state-2026-09-15.md).
Помилкові шляхи оригіналу збережені; автоматичного додаткового rollback
реалізація не вводить.

## Вхід і порядок роботи

Аргументи: 64-байтовий descriptor у RCX, selector у EDX, додатковий
64-бітний аргумент у R8. Функція починає з обнулення scratch count
`0x140D6C690` і чотирьох scratch pointers `0x140D6C698..0x140D6C6B7`.
Кількість рівнів читається як **signed int16 із descriptor `+0x3C`**.
Нульові й від'ємні значення повертають 1 після обнулення scratch.

Для кожного рівня резервується перший вільний `0x50`-байтовий запис через
`0x1403313F0`. Scratch count збільшується, адреса запису додається до scratch,
а record `+0x44` отримує номер рівня. Ці зміни передують нижчим helpers.
Перший запис зберігається окремо для успадкування palette base.

| Descriptor | Record | Підтверджена операція |
|---|---|---|
| `+0x10` word | `+0x04` | Копія на кожному рівні |
| `+0x12` word | `+0x08` | Рівень 0: копія; наступні: signed arithmetic shift, результат 0 замінюється на 1 |
| `+0x14` word | `+0x0A` | Рівень 0: копія; наступні: signed arithmetic shift, без clamp-to-1 |
| `+0x16` word | `+0x0C` | Так само, без clamp-to-1 |
| `+0x00` qword | `+0x10` | Рівень 0: копія адресного значення |
| `+0x2C + 4*(level-1)` dword | `+0x10` | Наступні рівні: попередній record `+0x10` плюс unsigned 32-bit delta |
| `+0x18` word | `+0x1C` | Копія, якщо descriptor `+8 != UINT64_MAX`; інакше `0xFFFF` |
| `+0x1A/+0x1C/+0x1E` words | `+0x20/+0x22/+0x24` | Копії лише в перший запис при наявності palette source |
| `+0x08` qword | `+0x28` | Копія лише в перший запис при наявності palette source |

На наступних рівнях source-значення накопичуються від попереднього запису,
а не обчислюються від першого. Зсуви і modulo-2^64 додавання перевірені,
включно з від'ємними 16-бітними значеннями та великими unsigned deltas.
Назви width/buffer-width спираються на попередню карту source records;
повний тип об'єкта за source-адресою цим проходом не встановлено.

## Додатковий аргумент і нижчі служби

Коли descriptor `+8 == UINT64_MAX`, palette helper взагалі не викликається,
навіть за ненульового додаткового аргументу.

За іншого значення `+8`, лише на першому рівні:

- record `+0x18 = (argument != 0)`;
- record `+0x1A` отримує молодші 16 біт selector;
- якщо argument ненульовий, `0x140331BD0(record, argument)` обробляє palette;
- його **молодший байт** результату визначає успіх;
- наступні записи копіюють record `+0x1E` з першого запису, вже після helper.

Успішний запис передається в `0x140331520(pool, record, 0, 0)`.
Його молодший байт результату теж є умовою успіху. Після цього
`0x1403310F0(pool, record)` записує word `+0x46 = 1` і позначає ділянки
карти зайнятості одиницями. Їхні адреси, signed lengths, округлення та gates
збігаються з відновленим очищенням `0x140330F60`.

`PtxRecordServices` залишає `0x140331BD0` і `0x140331520` явними зовнішніми
залежностями. Palette — робоча назва за полями/споживачем; повний контракт
аргументу, копіювання кольорів і placement policy ще не відновлені.

## Три шляхи відмови

| Причина | Адреси | Стан при поверненні 0 |
|---|---|---|
| Немає вільного record | `0x140336757/0x14033675A → 0x1403368CD` | Попередні рівні поточної текстури залишаються зарезервованими й позначеними |
| Palette helper повернув AL=0 | `0x14033685A/0x14033685C → 0x1403368CD` | Перший record уже зарезервований; rollback не викликається |
| Placement helper повернув AL=0 | `0x140336873/0x140336875 → 0x14033689B` | Для scratch-набору викликається `0x140331420`; записи обнуляються, позначені ділянки звільняються |

У третьому випадку scratch count і pointers **не обнуляються** після
звільнення записів. Їхній вміст не можна трактувати як список живих об'єктів
без урахування поверненого статусу.

Конкретний інтеграційний сценарій: доступні три записи, кожна текстура
потребує двох, bundle має три текстури. Перша текстура успішно створює
records 0/1. Друга резервує record 2 і отримує null при наступному запиті.
Loader звільняє records 0/1 зі свого payload. Record 2 залишається зайнятим;
кеш не отримує нового key/payload і повертає null. Сценарій повторений для
basic і variant через прямі loaders та через `CPtxManager`.

Allocation failure тут не підставлена заглушкою: виконується справжній
пошук `0x1403313F0` у заповненому пулі. Placement і palette залишаються
контрольованими межами; частота такого стану в запущеній грі не вимірювалася.

## Перевірки

```sh
python scripts/reverse/verify_ptx_materializer.py /path/to/dmc3.exe . data/reverse/ptx-materializer-20260916
```

Capstone 5.0.7, Unicorn 2.1.4, g++ C++20;
`-O2 -Wall -Wextra -Wconversion -Werror`.

У 71 сценарії порівняно весь pool `0xCB48`, payload `0x208`, manager
`0x4308`, immutable descriptor/source, 64-byte guards і порядок/аргументи
служб із хешами переданих записів. Перевірено:

- signed counts, 1–4 рівні, source deltas, arithmetic shifts і нульовий clamp;
- несуцільні вільні записи, перший і останній slot пулу;
- sentinel palette source, нульовий/ненульовий аргумент, усічення selector;
- результати helpers `0`, `0x100`, `0x101`, `0xFF`, тобто саме перевірку AL;
- вичерпання пулу після 0/1/2/3 резервувань;
- placement failure на кожному з чотирьох рівнів;
- ланцюги cache → loader → materializer → allocator/marker → cleanup;
- різний залишковий стан трьох помилкових шляхів.

Окремі host guards: п'ятий scratch slot і непозитивні довжини mark-span.
Вони обмежують представлену пам'ять C++ і не доводять аналогічної перевірки
в EXE. Вони також не надають транзакційного rollback.

Оригінальні materializer, allocator, marker, cleanup, loaders і cache
виконуються без заміни інструкцій. Перехоплені `0x140331BD0`, `0x140331520`,
а для зовнішніх сценаріїв також parser `0x1403365B0`, render finalizer
`0x140331A80` та CRT memset з перевіреним контрактом. Додаткові випадки з
нетиповими розмірами перевіряють механіку caller, не валідність такого ресурсу.

`evidence.json` містить адреси тіл, викликів і failure edges;
`verification.json` — усі сценарії, залишкові записи й хеші вихідних файлів.
Windows SEH, GPU acceptance, concurrency, reentrancy та aliasing не закриті.

## Далі

1. `0x140331520`: обчислення розміщення/довжин, політика вільних ділянок,
   причини відмови. Це найближча межа для заміни тестового placement contract.
2. `0x140331BD0`: точна структура palette argument і зміни її лічильників.
3. `0x140331A80`: render descriptors і зв'язок із graphics backend.
4. Перевірити, де scene/global lifecycle відновлює часткові резервування
   після прямого failure exit. Не позначати rollback завершеним до цього.
