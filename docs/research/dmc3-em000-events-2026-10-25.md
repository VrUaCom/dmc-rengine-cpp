# em000 family: every event code and every command gate (v123)

> Ported 2026-10-29 from the DMC Native Reader (`NR-Luna-v73`, `docs/research/dmc3-em000-events-v123.md`). Paths below that start with `app/` or `tools/research/` are the Reader's. In Rengine: the tables are `profiles/dmc3/em000_events.hpp` (data `src/profiles/dmc3/em000_events.inc`, test `tests/effect_catalogs_tests.cpp`); `tools/reverse/dmc3_gates.cpp` checks the handler `0x1401C3130` and the death state `0x140095E85`.

v77 and v78 mapped the enemy event handler and the scythe's code 3 by hand.
The Reader then played only code 3 and the death schedule. This version
plays every code that a CComEm000 command sends, from tables generated by
running the executable's code.

The generator is `tools/research/em000_events.py <dmc3.exe> <out.inc>` (it
needs `pip install unicorn`). It writes
`app/src/main/cpp/modules/motion/em000_events.inc` and uses an x64
emulator. Only codes, ids, joints, frames and table entries are written.

## 1. The handler (0x1401C3130)

The handler runs once for each code 0..0xCE, on a fabricated enemy:

- **Enemy.** Actor position (1, 2, 3), yaw 90 degrees, enemy type 0 and,
  in a second pass, type 0x1A.
- **Joints.** Entry k of `obj+0x6D8` points at a joint matrix at
  x = 10000 + 1000 k.
- **Given position.** (100, 200, 300).

Where a spawn goes is read in this order:
1. **A live parent.** The effect's `+0xC0` (mode = the prep argument) or
   `+0xC8` (mode at `+0xD4`), pointing at a joint matrix.
2. **The matrix it was given.** Its translation tells the given position,
   the actor position or a joint's world.
3. **The scale.** It is read from the code: the vector the scale helper
   `0x1403304F0` multiplies by. The emulator's matrix helpers do not give
   exact results, so the scale is not taken from the emulated matrix. Only
   code 3 is scaled (×2).

There are 123 rows over both enemy types. They agree with v77's table and
v78's death schedule. One addition: type 0x1A sends V838 instead of V132
for code 0x69.

## 2. The commands (CComEm000, vtable 0x1404C6A18)

- **Slot layout.** A command is the update in slot 2k+1 and the start in
  slot 2k+2. (Pairing slot 2k with 2k+1 gives wrong actions: for example,
  slot 235 with slot 234 plays action 87, whereas 235 with 236 plays action
  66, which is right.)
- **The run.** Each command runs its start once, then its update for 600
  frames. The fake interface answers:
  - `+0x40` with the frame, counted from the last action played;
  - `+0x48` (the motion's end) with false in one pass and true in another;
  - `+0x20` / `+0x28` (play a command of table 1 / 2) and `+0x80` (send a
    code) by recording them.
- **Repeats.** A code sent on every frame past its gate counts as one event.

## 3. The class tables

The (bank, action) byte pairs of CEm000..CEm004 (table 1 and table 2,
addresses in dmc3-effect-triggers-recon-v77.md) are copied as they are. A
command event becomes the (bank, action) of the class being shown. CEm000's
table 1 is the identity.

## In the Reader

- **One binding per spawn.** Every handler row is a binding of the em000
  profile.
- **The bridge.** For the action being played it spawns every event's rows:
  - on the body joint, by position or full world, with the scale;
  - at the enemy's origin, for the actor and given positions.
- **Death.** The death schedule is (tick, code), expanded from the same
  rows: the same 28 spawns as v78.
