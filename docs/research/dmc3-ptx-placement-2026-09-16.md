# DMC3 — placement, ініціалізація та зміна меж пулу PTX

Дата: 2026-09-16. Гілка: **Ада-Астра**.
База: `35a7fd1f5448a1f59ac8da283c71f0172084c836`.
EXE SHA-256: `e454272ed0fb0247fcbcf300e5d55d7a3e96d50b89b9ffaff81bb978dcbdd082`.

## Результат

На C++ відновлено три функції: placement `0x140331520`, ініціалізацію пулу
`0x140331910` та зміну резерву `0x140331D90`. **134 диференційні сценарії
PASS**. Для всіх **17 умовних переходів placement** виконано обидва виходи.
Це покриття конкретної функції й набору входів, не доказ повноти гри чи всіх
можливих комбінацій стану. Три host guards перевірені окремо.

Реалізація: `include/dmc_rengine/reverse/ptx_record_placement.hpp` та
`src/reverse/ptx_record_placement.cpp`. Попередня тестова заміна placement
у [матеріалізаторі](dmc3-ptx-materializer-2026-09-16.md) замінена реальною
реалізацією в нових інтеграційних сценаріях. Існуючі історичні receipts
залишені незмінними.

## Стан і адресація

| Поле | Підтверджене використання |
|---|---|
| `[0x140D6D300] +0x4C`, unsigned word | Початкове значення для pool base; зсув початку автоматичного сканування |
| `[0x140D6D300] +0x4E`, unsigned word | Верхнє значення для ініціалізації та віднімання резерву |
| Pool `+0xCB08`, dword | Початкова числова база |
| Pool `+0xCB0C`, dword | Межа, яку читають окремі гілки placement |
| Pool `+0xCB10`, dword | Копія верхнього значення після віднімання резерву |
| Pool `+0xCB14`, dword | Резерв, `wrap32(blocks << 5)` |
| Pool `+0xCB18`, dword | Верхнє значення мінус база, з 32-бітною wrap-поведінкою |
| Pool `+0x2800` | Початок карти зайнятості для досліджених операцій |

Назви позначають роль числових полів. Крок 32 підтверджений арифметикою
shift/division; цей прохід не прирівнює його до 32 байтів фізичної GPU-пам'яті.
Повна структура об'єкта конфігурації за `0x140D6D300` і його реальні значення
під час гри ще відкриті. `PtxPlacementConfig` явно передає два прочитані поля.

## Підготовка довжин

Аргументи placement: pool у RCX, record у RDX, requested index у R8D,
length mode у R9D. Нульовий index означає автоматичний пошук; ненульовий
трактується як signed 32-bit індекс іншої гілки.

Коли mode=0, record `+0x0E` встановлюється в 1 **до пошуку**. Якщо signed
record `+0x1C >= 0`, word `+0x44 == 0` і word `+0x18 == 0`, додаткова довжина
record `+0x26` теж стає 1. Інакше додаткова довжина для пошуку дорівнює нулю,
а саме поле `+0x26` зберігається. При mode != 0 використано наявні signed
16-бітні довжини, із тими самими gates для додаткової ділянки.

Матеріалізатор передає index=0, mode=0. Отже, його звичайний шлях задає
одну комірку для кожного запису плюс одну для відповідної першої palette
ділянки. Placement **не читає width, height чи format для розрахунку розміру**.
Навіть невдалий пошук залишає вже записані одиничні довжини.

## Автоматичний пошук

Початковий числовий індекс — `trunc_zero(int32(pool[+0xCB08]) / 32)`.
Адреса першого байта карти обчислюється окремо:

`pool + 0x2800 + trunc_zero(wrap32(base - uint16(config[+0x4C])) / 32)`.

Функція шукає послідовність нульових байтів довжиною image length + додаткова
length. Зайняті байти й закороткі вільні послідовності пропускаються; облік
індексу включає обидві частини. Знайдений початок записується в record `+6`
як молодші 16 біт `index << 5`. Якщо record `+0x18 == 0`, поле `+0x1E`
отримує `(index + image_length) << 5` із тим самим усіченням — незалежно
від решти gates, які визначали додаткову довжину.

Особливість меж: порівняння з `trunc_zero(pool[+0xCB0C] / 32)` виконується
під час пропуску **зайнятих** комірок. Нарощування вільної послідовності
окремої перевірки кінця не має. Сценарій з вільною послідовністю, довшою
за налаштований залишок, повертає успіх у справжньому EXE. Модель це зберігає.

## Заданий індекс

Гілка за ненульового requested index має власну поведінку:

1. Якщо index >= base/32, перевірка limit оминається. Інакше відмова
   стається лише при index >= limit/32. Це не звичайний тест належності діапазону.
2. Перевіряються байти від `pool +0x2800 + signed(index)` лише в кількості
   image length. Додаткова palette довжина не перевіряється.
3. У record `+6` записується `(base/32 + index) << 5` з усіченням до word.
4. Record `+0x1E` записується безумовно, включно з випадком `+0x18 != 0`.

Диференційні випадки підтверджують прийняття індексу вище limit і від'ємного
індексу, якщо прочитаний байт доступний і нульовий. Такі входи перевіряють
механіку EXE; їхнє використання справжніми callers не доведене. Жодна гілка
placement сама не позначає карту: це окремий `0x1403310F0` після успіху.

## Ініціалізація і зміна резерву

`0x140331910` передає `0x32D4` dwords до zero helper, тобто очищає **0xCB50**
байтів. Потім записує config `+0x4C` у pool `+0xCB08`, config `+0x4E` у
`+0xCB10`, різницю в `+0xCB18`. Поле scan limit `+0xCB0C` лишається нульовим.
Видимий memory extent більший на 8 байтів за попередній `PtxPoolImage`.
Новий `PtxPoolStorageImage` містить перевірений prefix і ці додаткові 8 байтів;
їх семантика, крім очищення, не присвоєна. Це не доказ повного розміру класу.

`0x140331D90(pool, blocks)`:

- записує `wrap32(blocks << 5)` у `+0xCB14`;
- віднімає це з config `+0x4E` і записує результат у `+0xCB0C/+0xCB10`;
- віднімає config `+0x4C` та записує різницю в `+0xCB18`;
- викликає `0x140315150` для глобального `CPtxManager` у `0x140D5B860`;
- повертає AL=1.

Додаткова перевірка встановила: records, карта зайнятості й хвіст пулу
зберігаються; у manager обнуляються ключі та лічильники, а padding і payload
зберігаються. Отже, це **не процедура звільнення всіх ресурсів**. Порядок
її виклику щодо інших teardown-функцій треба дослідити окремо.

У тесті виконується послідовність initializer → configure reservation →
materializer. Ця послідовність доводить сумісність відновлених функцій,
але не оголошується доведеним порядком запуску гри.

## Перевірки та межі

```sh
python scripts/reverse/verify_ptx_placement.py /path/to/dmc3.exe . data/reverse/ptx-placement-20260916
```

Capstone 5.0.7, Unicorn 2.1.4, g++ C++20;
`-O2 -Wall -Wextra -Wconversion -Werror`.

134 сценарії включають режими, усі palette gates, фрагментовані карти,
64 відтворювані випадкові карти, округлення signed division, 16/32-бітне
усічення, межові індекси, справжню нестачу місця, повторний cache lifecycle,
ініціалізацію та збереження payload при зміні резерву. Порівнюються вся
представлена пам'ять, guards, результати й послідовність викликів. Окремо
зафіксовано обидва результати всіх 17 conditional sites placement.

У прямих placement-тестах **немає перехоплених callees**: функція є leaf.
В інтеграції виконуються справжні placement, materializer, allocator, marker,
rollback, loaders і cache. Зовнішні тестові межі: palette helper
`0x140331BD0`, parser `0x1403365B0`, render finalizer `0x140331A80` та CRT
memset з точними контрактами `0x50` або `0xCB50` байтів.

Три host guards (непозитивна image length і адреса поза memory view)
обмежують C++-модель. Це не захист оригінального EXE та не гарантія rollback.
Live profile values, Windows SEH, GPU acceptance, aliasing, reentrancy і
concurrency не перевірені. `verification.json` зберігає всі 134 випадки,
branch outcomes і SHA-256 вихідних файлів; `evidence.json` — адреси й хеші тіл.

## Наступна ділянка

`0x140331BD0`: структура palette argument, копіювання й лічильники.
Далі — `0x140331A80` та повний тип graphics config за `0x140D6D300`.
Окрема lifecycle-задача: встановити callers initializer/configure і знайти
фактичне очищення ресурсів перед скиданням ключів кешу.
